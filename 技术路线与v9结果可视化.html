2. 技术路线

核心变化是把“候选发现”和“问题确认”拆开，让工具只取证，让 Agent 和人工复核负责判断。

1

证据底座

把 PT9L Markdown 文档构造成 Manifest、PageIndex、参数实例、RelationIndex 和全文检索材料。

2

项目画像

Project Scout Agent 建立型号、功能边界和文档范围判断，避免只凭风险文件定义产品功能。

3

动态派发

Orchestrator 读取 routing policy、项目画像、历史 agent_runs 和候选状态，动态生成 route_plan。

4

复审补证

领域 Agent 产出 finding 后，经过 Evidence Gate、Challenge 和最多 5 轮 Context Recovery。

5

分组报告

Dedup/Grouping 将重复 finding 收束为问题组，Report Agent 生成中文可审阅 HTML。

9. 人工修正案例：蓝牙问题

v9 中沉淀了一个关键人工修正组：MANUAL-BT-001。原报告曾将部分蓝牙相关描述理解为“PT9L 具备蓝牙功能，但缺少专项危害分析与验证关闭证据”。人工复核后确认，PT9L 实际没有蓝牙功能，设计输入、设计验证计划和设计验证报告均将蓝牙相关项目标记为不适用。

因此，正确整改方向不是补蓝牙验证，而是检查风险文件中出现的蓝牙/PT3SBT 相关描述是否属于范围冲突、模板残留或旧型号残留，并修订风险文件或补充正式适用性说明。

这个案例说明系统必须区分“风险文件中的一句描述”和“受控产品定义中的真实功能”。功能边界必须优先来自设计输入、说明书、软件需求/设计、验证计划/报告等权威文件。

11. 边界、风险与后续建议

必须人工复核

v9 报告是候选审查输出，不等于正式质量结论。高风险问题需要质量、法规、研发人员确认。

运行成本较高

系统真实调用多个 LLM Agent，并包含 Challenge、Context Recovery 和 Dedup/Grouping，比规则扫描慢。

审阅状态需导出

HTML 页面的人工勾选默认保存在 localStorage，正式交接前必须导出 JSON。

优先级 建议事项 目的
P0完成 61 个问题组的人工审阅，并导出 human-review-decisions.json。形成可交接、可复盘的人工判断结果。
P1新增“只基于已有 grouping_results.json 重新渲染 HTML”的轻量入口。避免每次调样式都重新调用 Dedup LLM。
P2用人工审阅结果建立 gold set，统计误报和漏报类型。持续提升 Project Scout、Challenge 和 Report Correction 规则。
P3在测试稳定后拆分当前主脚本。降低后续维护成本，但不建议为拆而拆。
