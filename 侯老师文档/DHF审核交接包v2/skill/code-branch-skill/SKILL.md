# Code Branch Skill（代码分支：固件常量 ↔ 文档三方对账）

## 目的

### 解决什么问题
DHF/DMR 里的阈值、量程、单位、版本号都是**人写的文档**：检验标准、设计输出、SRS、标签页。人会抄错、会版本漂移、会三处写三个值。而**固件常量是产品行为的最终真值**——机器实际执行的就是 `define.h` 里那几个数。本层的杀手锏：**当你确实拿到 C 固件工程时，把固件常量与文档逐条三方对账，代码当 ground truth 裁决文档。** 检验标准写"低压 2.6V"、设计输出写"2.4V"、固件写 `270/250`(=2.70/2.50V) 时，代码说了算，文档两边都得改。

### 朴素做法为什么不行
- **只信文档、不开源码**：三份文档自洽并不代表对——它们可能一起抄错同一个值，或都从旧版本漂移过来。没有代码这个独立真值，三方互证退化成"自说自话"。
- **不认正源直接全目录 grep**：源码工程里到处是同名 `.h`/`.c`，`*.si4project/Backup/` 下能有 30+ 个 `define(NNNN).h` 历史快照。**用编号副本对账 = 拿历史数据裁决，结论作废。** 这是本层最容易踩、也最致命的坑。
- **想当然换算定点常量**：固件常量几乎都是定点整数，标度各不相同（电压 ÷100，温度可能是 ADC 码/0.1℃/0.01℃）。不读注释和换算函数就 ÷100，会把对的判成错的。

### 一句话边界
本层只判"对不对得上 + 谁是真值"，**值本身在工程上对不对（该不该是 2.5V 关机）要看法规/风险/设计意图，由工程师/PM 拍**（见铁律 4）。

## 何时用本层

**先做这个判断，决定开不开本分支：**
- ✅ 开：你确实拿到了一个 **C 固件源码工程**——目录树里有 `FWLIB/`、`User/`、`*.uvprojx`(Keil) 或 `*.si4project`(Source Insight)。
- ❌ 不开：DHF 包里**通常没有源码**（源码在软件团队/MCU 供应商手里，DHF 只放 SRS、软件设计说明、V&V 报告）。只有 SRS/报告而无 `.c`/`.h` 工程时，**跳过本分支**，软件参数走 07 软件阶段轴 + 维度轴的数值一致维即可。

本层是**可选分支**，挂在最小动作链的末段：
`… 语义层(阶段轴+维度轴+去重+证伪) → 图纸分支 → (有源码则)本代码分支 → 汇总(错误总表+HTML)`。

## 输入

读这些之后才能下结论：
- **固件源码工程根目录**（占位符 `<CODE_ROOT>`，到你本机几乎一定不同，先确认真实路径）。典型形如 `D:/AI_0415/03DHF/<型号>/<...>_SRC_..._Vx.x.x/<...>_SRC_..._Vx.x.x`。
- **正源目录**：`<CODE_ROOT>/FWLIB/inc`、`<CODE_ROOT>/FWLIB/src`、`<CODE_ROOT>/User`、`HARDWARE/`、`APP/`（业务逻辑与全局宏在这）。
- **对账文档侧**（来自已转换的 `<型号>_MD`）：检验标准、设计输出、SRS/软件需求、软件版本记录、标签/包装/说明书相关 MD。
- **已有产物**：阶段轴产出的参数长表 `<型号>-运行参数长表.csv`（SSOT）、已有错误总表 `<型号>-错误总表.csv`（对账结论要并进去，且先去重）。

> 本 SKILL 正文里的所有数字、路径、宏名取自真实样本 `PT9S` 体温计固件（MCU=杭州士兰微 SD82P253，传感器 TSD14）。**新型号路径/宏名几乎一定不同，全是占位符，必须按实际工程自改。**

## 强制工作流（编号步骤，不许跳步）

> 平台说明：源方法论用的是 bash（`find`/`grep`）。本机 PowerShell 为主，但 **Bash 工具可直接跑下面的命令**；如走 PowerShell，请改用 `Glob`/`Grep` 工具或 `Get-ChildItem -Recurse` / `Select-String -Pattern`。命令里的 `<CODE_ROOT>`/`<型号>`/MCU 系列名/宏名都要按实际换。

### 0. 先加载通用工作方法 skill
- `D:/AI_0415/03DHF/skill/SKILL.md`（working-method）：读文件先确认工具在、实际看到才算数、诚实标 UNKNOWN、末尾回「喵」。

### 1. 认正源，排除旧副本（最容易踩的坑，先做）
判定规则：

| 目录 | 是否正源 | 说明 |
|---|---|---|
| `FWLIB/inc/`、`FWLIB/src/` | ✅ 正源（芯片库 + 全局宏） | 全局 `define.h`、外设驱动在这 |
| `User/`、`HARDWARE/`、`APP/` | ✅ 正源（业务逻辑） | 测温/校准/显示/按键逻辑 |
| `*.si4project/Backup/` | ❌ **旧副本，禁用** | Source Insight 自动备份，文件名带编号如 `define(7999).h`、`define(2988).h`，是历史快照不是当前代码 |
| `*.uvguix.*`、`Objects/`、`Listings/`、`DebugConfig/` | ❌ 编译产物 | 跟对账无关 |
| `.git/`、`~$*`、`*.bak` | ❌ | 同理 |

```bash
# 占位符：把 <CODE_ROOT> 换成你的固件工程根目录
CODE_ROOT="D:/AI_0415/03DHF/<型号>/<...>_SRC_..._Vx.x.x/<...>_SRC_..._Vx.x.x"

# 1) 找全局 define.h，先确认哪份是正源（应在 FWLIB/inc 或 User 下，不带括号编号）
find "$CODE_ROOT" -iname "define.h" | grep -vi "Backup"

# 2) 一眼区分正源 vs 副本：副本路径含 ".si4project/Backup" 且文件名带 (数字)
```

**辅助：用 `check_residue.py` 把整树副本当残留扫一遍**（确认没有把 Backup 当正源、也顺手抓他型号/血压计模板残留）：
```bash
python dhf_audit_toolkit\check_residue.py "<你的MD或源码目录>" --product <型号> --out 代码残留.csv
```
该脚本自动跳过 `dhf_audit_toolkit / _manifests / llm_wiki / __pycache__`，并区分"合法复用件"（`--allow-reuse`，默认 `PT5,PT3,T-Z1,Public,KD,PT1`）与"真残留"。**注意**：它不天然识别 `.si4project/Backup`，正源/副本的最终裁定靠本步规则人工拍。

**做不到的诚实边界**：`check_residue.py` 的"复用件 vs 残留"机器分不清，必须人工看是否合法沿用成熟机型；Backup 里 30+ 个 `define(NNNN).h` 哪份都不许用来对账（红线）。

### 2. grep 固件关键常量 + 身份（只搜正源，给行号）
正源定位后，**只 grep 正源目录**（`FWLIB/inc`、`User`），抓两类：**身份**（这份代码是谁）+ **行为常量**（机器实际阈值）。

**2a. 身份**（确认对的型号/版本，防止拿错工程对账）：

| 抓什么 | 在哪/怎么找 | PT9S 实测值（占位） | 对账谁 |
|---|---|---|---|
| MCU 型号 | `#include "SD82P253.h"`、库前缀 `SD82P253_*` | 士兰微 **SD82P253** | BOM / 原理图 / 设计输出 |
| 传感器型号 | 目录名/`sensor.h`/注释 | **TSD14** | BOM / SRS |
| 固件版本号 | `VER_NUM` / `VER_DATE` 等宏 | `VER_NUM 102`(=V1.0.2)、`VER_DATE 260430` | 软件版本记录 / 标签页 / DHF 版本 |

**2b. 行为常量**（裁决文档的真值，逐条对账）：

| 类别 | 宏名（占位，按实际改） | PT9S 实测 | 含义/换算 | 对账目标 |
|---|---|---|---|---|
| 低电压一级 | `VBAT_1ST_LINE` | `270` | 2.70 V（低电量提示） | 检验标准/设计输出"低压报警值" |
| 低电压二级 | `VBAT_2ND_LINE` | `250` | 2.50 V（关机/禁测） | 检验标准"欠压关机值" |
| 电压恢复 | `VBAT_RST_LINE` | `300` | 3.00 V（解除低压） | 设计输出"恢复阈值" |
| 量程上限 | `TAMB_HI_LINE` | `4100` | 环温/测量上限阈值 | SRS 量程 / 检验标准 |
| 量程下限 | `TAMB_LO_LINE` | `500` | 环温/测量下限阈值 | SRS 量程 / 检验标准 |
| ℃/℉ 默认 | `UNIT_F_VERSION`/`UNIT_C_VERSION` | F=1, C=0 | 出厂单位版本开关 | SRS"默认温标"/包装/说明书 |

```bash
# 只搜正源，排除 Backup/编译产物。-rn 给行号便于回溯到具体宏
INC="$CODE_ROOT/FWLIB/inc"; USR="$CODE_ROOT/User"

# 身份
grep -rn -iE "VER_NUM|VER_DATE|VERSION" "$INC" "$USR"
grep -rn -iE "#include .*(SD82|STM32|HC32|N32|MM32|nRF|ESP)" "$INC" "$USR"   # MCU 系列名按实际换

# 行为常量（阈值/量程/单位/电压/关机/标定）
grep -rn -iE "VBAT|BATT|VOLT|LOWBAT" "$INC" "$USR"
grep -rn -iE "AUTO.?OFF|POWER.?OFF|SHUTDOWN|SLEEP.*TIME" "$INC" "$USR"
grep -rn -iE "HI_LINE|LO_LINE|LIMIT|RANGE|OVER|UNDER" "$INC" "$USR"
grep -rn -iE "UNIT|FAHREN|CELSIUS|_F_|_C_" "$INC" "$USR"
grep -rn -iE "CALI|CALIB|ADJUST|OFFSET|COMPENSAT" "$INC" "$USR"
```
通用还要 grep（不同产品名不同）：**自动关机时间**(`*AUTO_OFF*`/`*POWEROFF*`/`*SHUTDOWN*`)、**标定/校准表**(`*CALI*`/`*ADJUST*`/查找表数组)、**测量上下限/超温报警**(`*HI*`/`*LO*`/`*LIMIT*`/`*OVER*`)、**默认温标/单位**(`*UNIT*`/`*FAHREN*`/`*CELSIUS*`)、**电池/电压**(`*VBAT*`/`*BATT*`/`*VOLT*`)、**版本**(`*VER*`/`*VERSION*`/`*FW*`)。

> **定点标度铁律**：固件常量几乎都是定点整数，需按代码里的标度换算（电压 `270`→ ÷100 = 2.70 V；温度常量可能是 ADC 码、0.1℃ 或 0.01℃，**必须读取注释/换算函数确认标度，别想当然 ÷100**）。换算依据写进对账记录。

### 3. 三方对账（代码裁决文档）
把抓到的每个常量与文档逐条对，结论列**代码值为准**：

| 项 | 固件(正源, 真值) | 检验标准写 | 设计输出/SRS 写 | 裁决 | 动作 |
|---|---|---|---|---|---|
| 低压一级 | 2.70 V (`VBAT_1ST_LINE=270`) | 2.6 V | 2.6 V | **2.70** | 检验+设计均改 2.70，或确认是否代码需改 |
| 低压二级 | 2.50 V (`VBAT_2ND_LINE=250`) | 2.4 V | — | **2.50** | 同上 |
| 默认温标 | F (`UNIT_F_VERSION=1`) | — | 说明书写默认℃ | **F** | 核实出厂烧录版本，文档对齐 |
| 固件版本 | V1.0.2 (`VER_NUM=102`) | 标签 V1.0.1 | DHF V1.0 | **V1.0.2** | 版本记录补齐 |

**裁决方向不是绝对"代码永远对"**：代码是"机器实际行为"的真值。若文档是**法规/安规约束的设计意图**（如标准要求欠压必须 2.5V 关机）而代码写错，则反过来——**判定为固件缺陷，开 CAPA/软件变更**。每条对账标注：①代码值 ②文档值 ③哪个是"应然"（看法规/风险/设计意图）④结论是改文档还是改代码。

**可选：把对账数值喂确定性数值检查器复核**。把固件值与文档值整理成参数长表行（列含 `参数名/值/出处文件/阶段`，固件那行 `出处文件` 写正源路径:行号），跑：
```bash
python dhf_audit_toolkit\check_params_numeric.py 参数明细.csv --product <型号> --out 数值冲突.csv
```
它做单位归一 + 区间/边界/单点签名比对，**近零误报**（`34-43` vs `34~43` 不报，归一后真冲突才报）。注意它对**低压阈值按电压 V 不做换算**（脚本里 `cp=="低压阈值": return v` 的特判），别把电流换算套上去。**精度/分辨率它主动不做确定性比对**，交语义层。

### 4. 产出（接到主错误总表）
对账结果并入主审核错误总表，每条至少含：
`项目 | 固件正源值(文件:行) | 文档值(文件:位置) | 差异 | 裁决依据 | 结论(改文档/改代码/CAPA)`

- 固件侧引用务必写**正源相对路径 + 行号**（如 `FWLIB/inc/define.h:84 VBAT_1ST_LINE=270`）。
- **严禁引用 `*.si4project/Backup/define(NNNN).h`** —— 这是审核作废的红线。
- 严重度按主审核口径：身份污染（拿错工程/型号）、安规相关阈值代码与设计意图冲突偏 critical/major；纯文档抄错偏 major/minor；值本身存疑（待工程师拍）**不要误升级成 critical**。
- 写回错误总表后，过一遍证据核验（见步骤 5）。

### 5. 证据核验（接自验证层）
对账 finding 并入错误总表后，跑根目录 `verify_findings.py` 核验"引文是不是真的存在于语料/源码里"：
```bash
python verify_findings.py
```
它对每条 finding 的引文回语料搜，五分类裁决。**关键接缝**：本层会产生"全文无 X""固件未定义某宏"这类**缺失断言**——`verify_findings.py` 用 NEG 关键词（`无/未/缺/NEI`）专门特判，不会把这类真缺失误杀成"可疑/幻觉"。它只验"引文存不存在"，不验"结论对不对"（一致性≠正确性，值本身对不对工程师拍）。

## 边界与踩坑（诚实标注）

- **正源/副本机器分不清最后一公里**：`check_residue.py` 不天然识别 `.si4project/Backup`；正源裁定靠步骤 1 的目录规则 + 人工。**用编号副本对账 = 结论作废。**
- **定点标度不能臆测**：温度常量是 ADC 码 / 0.1℃ / 0.01℃ 全有可能，必须读注释和换算函数确认，换算依据入对账记录。
- **`check_params_numeric.py` 是低召回换近零误报**：它只报归一后仍冲突的，解析不了的直接跳过；精度/分辨率不做确定性比对。它的输入长表是你手抽的——抽漏了它无能为力。**它只查"对不对得上"，值本身对不对要工程师拍。**
- **`verify_findings.py` 只验引文真伪，不验结论正确**：引文真实 ≠ 判定正确（焊点数 vs 线数本不是一回事这类逻辑错它管不了，靠对抗证伪 CoVe + 裁决库）。
- **跨表/跨源对账非近零误报**：身份/版本/常量的跨文档对账是"候选生成器 → 进人审"，不是自动放行；LLM 抽取与人工换算都可能有瑕疵。
- **平台锁定与中文路径**：源码工程路径常含版本号目录嵌套、可能有中文/空格——脚本里不要硬编码中文路径，从 Path/manifest 读；终端中文乱码时用 `Path.exists()` 判存在，别信终端显示。
- **schema 字段名必须 ASCII**：若把对账结果喂多智能体 workflow，结构化 schema 的 property key 用英文（`dwg_no`/`severity`/`code_val`），**值照填中文**，否则 API 直接 400 整批失败。
- **铁律照旧**：①下游≥上游（固件实现值不得收窄规格）②正文/源码逐字封闭（标题/文件名/空宏注释不算证据）③仅美国时 EN/GB 反向引用=真错 ④一致性≠正确性。
