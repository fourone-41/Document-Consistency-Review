# 方案架构问题分析与改进方向

> 2026-06-11 | 基于 10 个样本文件的实践复盘

---

## 一、原方案的大方向问题

### 问题 1：过度依赖 LLM "一次性正确输出"

**原设计假设**：给 LLM 一个 prompt + 文档内容，它会返回格式完美的 JSON。

**实际情况**：
- LLM 约 60% 的返回存在格式问题（未转义引号、字符串内换行、markdown 包裹）
- JSON 越大越容易出错（超过 4000 token 的输出几乎必定有格式瑕疵）
- 不同 LLM 行为不一致，换模型后可能全部重跑

**根本原因**：把 LLM 当成确定性 JSON 生成器来用，缺乏容错层。

**改进方向**：
- ✅ 已实现：健壮的 `try_parse_json`（状态机修复未转义字符）
- 🔲 待做：引入 JSON Schema 校验层，对缺失字段自动补 null，对多余字段自动忽略
- 🔲 待做：失败时自动重试（换 prompt 或减小 chunk），不是直接返回空

---

### 问题 2：Chunk 策略与文档结构脱节

**原设计假设**：文档按 `## ` 标题分割即可。

**实际情况**：
- 医疗器械 DHF 文档大量是表格形式（Excel 转 Markdown），没有标题结构
- 一个 85000 字符的开发计划表变成一整个 chunk 发送，LLM 直接截断
- 小 chunk（242 字符的空白首部）浪费一次 API 调用且 LLM 回复"无内容"

**根本原因**：用通用文本分割策略处理结构化表格文档。

**改进方向**：
- ✅ 已实现：多级分割策略（标题→表格行→强制按行切割）
- 🔲 待做：针对表格型文件，按表格边界分割而不是按字符数
- 🔲 待做：chunk 前做预处理——去掉纯空白/签名区块，避免浪费 API 调用
- 🔲 待做：chunk 间传递上下文摘要（当前每个 chunk 独立抽取，跨 chunk 的实体会重复）

---

### 问题 3：信息抽取的"结构化陷阱"

**原设计假设**：所有文档内容都可以映射到预定义的结构化节点。

**实际情况**：
- "预期用途"、"质量要求"、"测试背景"等大段描述性文字无法结构化
- 强行结构化会导致信息丢失或失真
- 一些关键约束信息（如"测试环境要求"）被丢弃

**根本原因**：schema 设计偏向"数据库字段"思维，缺少对自由文本的容纳机制。

**改进方向**：
- ✅ 已实现：`SemanticFragment` 作为兜底，保留原文可溯源
- ✅ 已实现：`HAS_DETAIL` 边将 Fragment 链接到父结构节点
- 🔲 待做：控制 Fragment 粒度——目前开发计划表产出 122 个 Fragment，需要合并策略
- 🔲 待做：对 Fragment 做二次分类/标签化，方便后续检索

---

### 问题 4：关系抽取严重不足

**原设计假设**：通过一次 LLM 调用就能发现文档中的所有关系。

**实际情况**：
- V1 版仅 31 条边（对 540 个节点），关系密度极低
- LLM 对"隐含关系"不敏感（如 Person 出现在 PlanTask 的 owner 字段 → RESPONSIBLE_FOR）
- 跨文件关系完全缺失

**根本原因**：只靠 LLM 推理关系，没有利用数据本身的结构线索。

**改进方向**：
- ✅ 已实现：规则引擎 + LLM 双轨策略（当前 1183 条边）
- ✅ 已实现：从节点字段中推导关系（owner→RESPONSIBLE_FOR, source→EXTRACTED_FROM）
- 🔲 待做：跨文件关系推导（如 Requirement ↔ Test 的 VERIFIES 关系需要跨文件匹配）
- 🔲 待做：基于术语归一化结果做实体对齐，再推导跨文件边

---

### 问题 5：文档类型识别过于粗放

**原设计假设**：按目录名匹配文档类型即可。

**实际情况**：
- 评审检查表在"软件设计方案"目录下 → 被错误分类为 software_design
- 检测报告在"T1样机"目录下 → 被笼统分类为 t1_prototype
- 分类错误直接导致使用了错误的抽取 prompt → 节点类型不匹配

**根本原因**：文件组织结构不等于文档语义类型。

**改进方向**：
- ✅ 已实现：文件名关键词优先于目录名匹配
- 🔲 待做：对不确定类型的文件，先用 LLM 做一次轻量分类（读前 500 字判断类型）
- 🔲 待做：允许一个文件同时具有多个类型特征（如"带评审记录的设计输入"）

---

### 问题 6：缺乏质量验证环节

**原设计假设**：跑完管道即可使用。

**实际情况**：
- 多个文件抽取结果为空，但管道不报错
- 直到用户在 Neo4j 查询时才发现 Test 节点为空
- 没有自动化的 "期望 vs 实际" 检查

**根本原因**：管道缺少断言/校验层。

**改进方向**：
- 🔲 待做：Step1 后自动校验——如果源文件 >1000 字但输出节点为 0，标记为异常并重试
- 🔲 待做：对比 "文件表格行数" 与 "抽取出的节点数"，差距过大则报警
- 🔲 待做：生成抽取覆盖率报告（哪些段落被结构化、哪些被 Fragment 兜底、哪些被完全忽略）

---

### 问题 7：实体去重与归一化缺失

**原设计假设**：每个 chunk 独立抽取后简单合并。

**实际情况**：
- 同一个 Person（如"项目工程师"）在 17 个 chunk 中被抽取 17 次 → 115 个 Person 节点
- 同一个 Product "PT9L红外体温计" 在不同文件中有不同表述
- Neo4j 中产生大量重复节点，影响图查询和一致性校验

**根本原因**：缺少跨 chunk / 跨文件的实体消歧与合并机制。

**改进方向**：
- 🔲 待做：Chunk 合并时对 Person/Product/Regulation 做去重（基于名称相似度）
- 🔲 待做：利用已有的 `terminology.yaml` 做术语归一化
- 🔲 待做：Neo4j 导入时用 MERGE 而不是 CREATE，基于 (name + source) 做唯一约束

## 二、建议的改进优先级

| 优先级 | 改进项 | 预期收益 | 工作量 |
|--------|--------|---------|--------|
| P0 | 抽取失败自动重试 + 质量校验 | 避免静默丢失数据 | 0.5天 |
| P0 | 实体去重（Person/Product） | Neo4j 图可用性提升 | 1天 |
| P1 | 跨文件关系推导 | 实现一致性检查的前提 | 2天 |
| P1 | 表格型文件专用 chunk 策略 | 减少 API 调用、提升抽取完整性 | 1天 |
| P2 | LLM 预分类文档类型 | 提升泛化能力 | 0.5天 |
| P2 | SemanticFragment 合并与标签化 | 减少噪音 Fragment | 1天 |
| P3 | 抽取覆盖率报告 | 可视化信息损失 | 1天 |
| P3 | 全量文件处理 + 增量更新 | 生产可用 | 2天 |

---

## 三、核心结论

原方案的最大问题不是某个具体 bug，而是 **对 LLM 输出的信任度过高** 和 **缺乏中间验证环节**。整个管道是"乐观路径"设计——假设每一步都正确，一旦某步出错就静默丢失数据。

正确的架构应该是：

```
输入 → 预处理(分类+分割) → LLM抽取 → 格式修复 → Schema校验 → 质量检查 → 实体去重 → 关系推导 → 输出
         ↑                                              ↓
         └──────────── 失败重试 ←── 异常检测 ←─────────┘
```

当前已经修复了"格式修复"层（`try_parse_json`），下一步重点应放在"质量检查"和"实体去重"上。
