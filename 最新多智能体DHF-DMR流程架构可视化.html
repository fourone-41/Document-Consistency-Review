这版按你给出的结构绘制：不是复杂环形线路，而是清楚展示 Orchestrator 如何连接工具、候选发现、领域 Agent 和补证闭环。

这张图想表达什么

Orchestrator 是调度中心

它不是普通 workflow 节点，而是生成任务、路由候选、组织补证、重新派发的中心。

Candidate Discovery 不直接裁决

它只提出候选假设。候选先回到 Orchestrator Candidate Router，再进入领域 Agent 复审。

工具只是取证能力

PageIndex、Relation Index、全文检索、文件读取都只提供证据和上下文，不直接生成 finding。

Orchestrator 的调度边界

Orchestrator 做什么 具体动作 不做什么
生成必查任务 按阶段轴 x 维度轴生成任务矩阵，保证生命周期闭环和横向覆盖。 不因为没有候选就跳过必查项。
路由候选 标准化、去重、合并、绑定必查任务，分派一个或多个领域 Agent。 不做 confirm / dismiss，不直接输出 finding。
组织补证 根据 Context Recovery 的缺口诊断，重新派发补证任务。 不让同一个长 prompt 无限重跑。

Agent 回流结果如何处理

回流结果 Orchestrator 下一步
候选假设进入 Candidate Router，分派给一个或多个领域 Agent。
confirm送 Evidence Gate 和 Challenge 验证。
dismiss记录驳回理由，可写入裁决库。
needs_more_context送 Context Recovery 诊断缺口，再回 Orchestrator 派补证任务。
human_review进入人工复核包，不再自动循环。

Context Recovery 五轮补证

每一轮都会回到 Orchestrator 再派发，不是同一个 prompt 变长后硬跑。

1

局部上下文

补原证据前后行、完整表格行列、小节标题和文件基本信息。

2

同实体跨文件

补同一型号、料号、参数、文件编号、需求编号或风险编号的全项目出现位置。

3

生命周期上下游

补设计输入到输出、风险到控制到验证、BOM 到工艺到检验的链路。

4

版本受控状态

补封面、修订历史、签批页、文件清单、变更记录、归档或废止信息。

5

反证与人工包

整理支持 confirm 的证据、支持 dismiss 的反证、仍缺证据和人工复核建议。
