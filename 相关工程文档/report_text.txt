Document-level RE（文档级关系抽取）单文件内的长距离关系抽取：实体的关系往往需要跨多个句子甚至多个段落才能判断，以下三项技术分别解决「上下文定制」「推理依据定位」「任务分解」三个子问题。A1. ATLOP论文Document-Level Relation Extraction with Adaptive Thresholding and Localized Context Pooling来源AAAI 2021 · github.com/wzhouad/ATLOP解决的核心问题：同一个实体节点和不同实体配对时，判断关系所需要的上下文完全不同，但传统方法所有配对共用同一个实体 embedding，导致信息混乱。两项核心技术：局部上下文池化（Localized Context Pooling）：用 BERT 编码整个文档后，对每个实体对 (eₛ, eₒ) 单独计算注意力分布 q(s,o)——这个分布告诉模型「判断这对实体的关系时，文档里哪些位置最值得关注」。用 q(s,o) 对所有 token 向量加权求和，得到这对实体专属的上下文向量。最终关系表示 = 实体向量 + 专属上下文向量，不同实体对拿到的上下文各不相同。自适应阈值（Adaptive Thresholding）：同一对实体可能同时满足多种关系（多标签问题），ATLOP 为每个实体对学习一个专属阈值，而非用统一固定阈值来决定哪些关系被激活。对本项目的应用思路：ATLOP 的核心洞察是——模型判断某对实体关系时，真正有用的上下文是注意力权重高的片段，而不是位置上靠近这两个实体的句子。这两者往往不是同一回事。例如判断 Risk-01 和 CM-03 的关系，文档里最关键的句子可能不在 Risk-01 的定义段落附近，而是在「风险评估结论」章节里一句「采用校准补偿方案可将偏移量控制在允许范围内」。A2. DREEAM论文Guiding Attention with Evidence for Improving Document-Level Relation Extraction来源EACL 2023 · arxiv.org/abs/2302.08675解决的核心问题：关系抽取完成后，如何确定「判断这条关系到底看了文档里哪几句话」——即找到支持关系判断的证据句子，同时不引入额外的证据分类器（避免内存翻倍和标注数据稀缺的问题）。核心洞察：ATLOP 在计算每个实体对关系时，已经产生了注意力分布 q(s,o)。这个分布不仅用于生成上下文向量，本身就包含了「模型在判断这条关系时更关注文档哪些位置」的信息——注意力权重高的句子，就是证据句子。DREEAM 在训练时加了一个辅助信号：强制让注意力分布在人工标注的证据句子上权重更高，测试时直接用注意力排名输出证据，不增加任何额外参数。对本项目的应用思路：DREEAM 提供了一个重要的工程启示——关系判断和证据定位可以是同一个过程的两个输出，而不是两个独立步骤。对本项目而言，Claude 判断节点关系时的推理过程就是它的「注意力」，这个过程天然包含了「它看了哪里」的信息。具体做法是在 Step2 和 Step4 的 prompt 里加一条强制要求：Claude 必须在给出关系类型的同时，明确引用它判断所依赖的原文句子。这些句子不是随机选取的「附近上下文」，而是 Claude 认为构成判断依据的逻辑关键句——二者有本质区别。输出格式中新增 evidence_spans 字段：{&#10; &quot;source&quot;: &quot;Risk-01&quot;,&#10; &quot;target&quot;: &quot;Test-T12&quot;,&#10; &quot;relation&quot;: &quot;VERIFIED_BY&quot;,&#10; &quot;confidence&quot;: 0.87,&#10; &quot;evidence_spans&quot;: [&#10; {&#10; &quot;doc_id&quot;: &quot;06_硬件设计方案&quot;,&#10; &quot;section&quot;: &quot;3.2 校准流程&quot;,&#10; &quot;text&quot;: &quot;出厂前须完成传感器漂移校准，覆盖35-42℃范围&quot;,&#10; &quot;char_offset&quot;: [1240, 1298]&#10; },&#10; {&#10; &quot;doc_id&quot;: &quot;12_测试报告&quot;,&#10; &quot;section&quot;: &quot;4.1 T-12校准验证&quot;,&#10; &quot;text&quot;: &quot;T-12测试验证了红外传感器在高温环境下的线性度&quot;,&#10; &quot;char_offset&quot;: [334, 385]&#10; }&#10; ]&#10;}这个字段有两个用途：一是审查报告里的精确定位（每条问题都能溯源到原文）；二是质量评估——如果 Claude 给出的证据句子和关系判断逻辑上对不上，说明这条边的置信度应该被降低，可以作为 candidate 而非直接写入图。A3. AutoRE论文Document-Level Relation Extraction with Large Language Models来源ACL 2024 · github.com/THUDM/AutoRE解决的核心问题：直接让 LLM 从大量关系类型里一步选择效果差；同时「哪两个节点之间有关系」这个候选对生成问题，比「这两个节点是什么关系」更难解决，两者不能混为一谈。RHF（Relation-Head-Facts）范式：把文档级 RE 分解为三个串行子任务，每步任务更聚焦，LLM 错误率明显低于一步到位：任务 1 关系检测：输入整个文档，输出「这个文档里存在哪些关系类型」，直接过滤掉根本不存在的类型。例如一份纯硬件设计方案文件，里面根本不会有 SCHEDULES_SOFTWARE 这类边，无需为它生成任何候选对。任务 2 头实体识别：输入文档 + 某种关系类型，输出「哪些实体是这种关系的发出方（head entity）」。例如确认文档里存在 MITIGATED_BY 后，找出所有作为 MITIGATED_BY 源头的 Risk 节点。任务 3 尾实体预测：输入文档 + 关系类型 + 头实体，输出对应的尾实体。例如已知 Risk-01 是某个 MITIGATED_BY 的源头，找出对应的 RiskControl 节点是哪个。对本项目的应用思路：AutoRE 真正解决的是候选对爆炸问题——它不让模型在所有节点对上做穷举，而是先让模型在文档层面判断「有哪些关系类型存在」，用这个判断来约束后续的实体搜索范围。这个思路对 Step2 的改造价值在于：把现在的 Step2「给节点 A 和节点 B，判断是什么关系」拆分为 Step2a 和 Step2b：Step2a 输入整个文档和 edges.yaml 关系类型列表，输出「该文档中存在哪些关系类型」；Step2b 针对每个被确认存在的关系类型，再去找对应的实体对。这样 Step2a 相当于一个低成本的过滤器，大量不相关的关系类型在文档层面就被排除，后续只在有意义的类型上做精细配对。B. Cross-document RE（跨文档关系抽取）跨文件实体-关系-实体的发现与分类：给定来自不同文件的两个节点，判断它们之间是否存在关系及关系类型。B1. CodRED论文A Cross-Document Relation Extraction Dataset for Acquiring Knowledge in the Wild来源EMNLP 2021 · github.com/thunlp/CodRED跨文档关系抽取领域的奠基性数据集和基线框架，提出了「文本路径（Text Path）」核心概念：两个文档里的实体往往通过一个桥接实体相连，文本路径是从头实体出发、经过桥接实体、到达尾实体的证据链。文档A（风险分析）：Risk-01 涉及「红外传感器」的漂移&#10; ↓ 桥接实体：「红外传感器」同时出现在两个文档&#10;文档B（测试报告）：「红外传感器」的校准验证由 T-12 完成&#10;→ 文本路径：[Risk-01描述] + [红外传感器桥接描述] + [T-12描述]&#10;→ 推断：Risk-01 VERIFIED_BY T-12基线模型三步：①给定头尾实体，从文档库找相关文档构建候选路径；②从候选路径中选最相关的证据句子；③基于证据做关系分类。本项目比 CodRED 更有利：文档集合已知（254 份），无需检索，直接用 closed setting。对项目的直接应用：在 merge_results.py 中加入桥接实体查找逻辑——找同时被两个文档引用的 Product / Identifier / Person 节点作为桥接实体，将「源节点上下文 + 桥接描述 + 目标节点上下文」三段文本一起送给 Claude，而非只送两个孤立节点的 description。B2. KXDocRE论文Knowledge-Driven Cross-Document Relation Extraction来源arXiv 2024 · arxiv.org/abs/2405.13546解决的核心问题：跨文档 RE 中，两个实体的描述可能非常简短或术语化（如「Risk-01」「T-12」这样的编号），仅凭原文难以判断关系。引入外部领域知识后，「Risk-01 是 ISO 14971 框架下的风险项，T-12 是 ISO 13485 7.3.6 条款要求的验证测试」，则 ISO 14971 第 8 章明确规定风险控制措施必须经测试验证，关系判断变得清晰。框架三个组件：实体知识嵌入：对每个节点，除原文描述外，注入实体类型、所属法规框架、相关条款编号。跨文档上下文融合：把两个文档的相关段落编码后融合，让模型看到两个文档的「对话」而非孤立地看各自文档。知识引导的关系分类：把法规规则作为约束注入分类过程，如「根据 ISO 14971，Risk 和 Test 之间最可能的关系是 VERIFIED_BY 或 MITIGATED_BY，请优先在这两种中判断」。对项目的直接应用：Step4 的 prompt 模板加入「所属法规框架」和「法规知识引导」两个字段，系统化地把 ISO 法规条款注入每次跨文件关系判断，项目已有的法规知识引导表正是这一思路的体现。B3. HCRE论文LLM-based Hierarchical Classification for Cross-Document Relation Extraction with a Prediction-then-Verification Strategy来源arXiv 2025 · arxiv.org/abs/2604.07937核心发现：直接让 LLM 从 30+ 种边类型中一步选择，效果反而不如专门训练的小模型，原因是选项太多、语义相近时 LLM 在 VERIFIED_BY / COVERS / REPORTED_IN 等相近选项间容易犯错。解法：把预定义关系组织成层级树，LLM 逐层做「少选一」的判断，每层加预测-验证步骤：第 1 轮（粗分类，4 选 1）：这对节点属于哪个大类？结构/定位类 / 追溯链 / 验证测试链 / 风险管控链第 2 轮（细分类，4 选 1）：在「验证测试链」内，具体是什么关系？VERIFIED_BY / COVERS / REPORTED_IN / MEASURES第 3 轮（验证，仅低置信度时触发）：确认判断，或排除相近类型。对项目的层级树建议：粗类细分关系结构/定位类PART_OF · STATED_IN · INDEXES · LISTS_FILE追溯链DERIVES_FROM · IMPLEMENTS · REFERENCES · RELATES_TO验证测试链VERIFIED_BY · COVERS · REPORTED_IN · MEASURES · HAS_MEASUREMENT风险管控链MITIGATED_BY · CONSTRAINED_BY · ADDRESSED_IN对齐/裁决类CORRESPONDS_TO · CONFLICTS_WITH · POTENTIALLY_CONFLICTS每个粗类对应一次 LLM 调用，平均 2–3 次调用即可到达叶节点，比一步 30+ 选项的准确率更高，总成本还可能更低（大量配对在第 1 轮就被判为「无关」而跳过）。B4. MAQD论文Evidence Selection via Multi-Aspect Query Diversification for Cross-Document Relation Extraction来源Springer JIIS 2025 · link.springer.com/article/10.1007/s10844-025-00952-6解决的核心问题：同一个事实在不同文档里用完全不同表述出现，单一向量查询只能命中其中一种表述，导致候选节点召回不全。「传感器漂移」这个 Risk 在不同文档中可能被描述为「红外传感器在高温下的偏移量超出允许范围」「针对温度漂移问题的校准补偿方案」「高温环境传感器线性度验证」等，单一查询无法全覆盖。多角度查询生成（Multi-Aspect Query Diversification）：对每个节点生成多个角度的查询，各角度分别检索后取并集，再用 cross-encoder 重排：对节点 Risk-01（「红外传感器偏移导致测量误差」），生成5个角度查询：&#10; 角度1（问题描述）：「传感器漂移 偏移 误差」&#10; 角度2（影响对象）：「测量精度 准确度 允差」&#10; 角度3（物理机制）：「红外传感器 温度 线性度」&#10; 角度4（法规视角）：「ISO 14971 风险 危害」&#10; 角度5（解决方向）：「校准 补偿 验证」&#10;&#10;候选 = union(各角度 top-10 检索结果)&#10;最终候选 = cross_encoder 重排后 top-20对项目的直接应用：Step4 候选节点召回从单一 description 相似度匹配，改为多角度查询（节点描述 + 术语归一主题词 + 节点类型属性 + 法规框架术语 + 数值指标），直接提升召回率，解决「功能→测试 151% 误报」问题中召回侧的遗漏。C. Graph-RAG 用于需求追溯和合规检查论文Leveraging Graph-RAG and Prompt Engineering to Enhance LLM-Based Automated Requirement Traceability and Compliance Checks来源arXiv 2024 · arxiv.org/abs/2412.08593与本项目场景最直接对应的论文：SRS 文档 ↔ DHF 文档，法规标准 ↔ ISO 13485/14971/IEC 62304，「需求是否符合高层法规」↔「文档是否满足一致性要求」。在金融监管（券商 SRS 对照股市标准）和航空航天（NASA X-38 容错系统）两个受监管场景中验证，Graph-RAG + CoT/ToT 显著优于朴素 RAG。框架流程：预处理：把待检查文档和参考法规文档清洗、分块。图构建：LLM 抽取实体和关系，为每个图元素生成语义摘要；Leiden 社区检测；对每个社区生成摘要并建向量索引。检索：本地检索（节点向量 ANN + 沿边扩展）用于精确追溯查询；全局检索（社区摘要 ANN + Map-Reduce）用于覆盖率审查。合规判断：检索到相关法规内容后，用 Chain-of-Thought（CoT）让 LLM 逐步推理「这条文档内容是否违反该法规条款」；对不确定性高的情况，用 Tree-of-Thought（ToT）并行探索多条推理路径，选最可信的结论。论文坦承的局限：依赖完整准确的输入数据，成本较高，需要针对特定场景仔细调整——对项目意味着需要在小规模样本上验证效果后再全量铺开。D2. 远程监督闭环（大规模训练数据自动生成）核心思路：用已知的结构化知识（ISO 法规条款）自动标注非结构化文档（DHF 文档），大规模生成领域训练数据，无需人工标注。原理：「如果 ISO 14971 第 8 章规定风险控制措施必须经过验证测试，那么 DHF 文档中所有同时出现风险控制措施和测试记录的段落，都是 VERIFIED_BY 关系的候选正样本。」这和 Wikidata ↔ Wikipedia 的对齐方式在方法论上完全一致。在项目中的具体实施：从 ISO 法规中提取已知的关系三元组（如「风险控制措施 VERIFIED_BY 验证测试」「设计输入 DERIVES_FROM 用户需求」）。在 DHF 文档中定位同时出现相关实体的段落，自动标注为对应关系的训练样本。用生成的样本 fine-tune 一个轻量分类模型，替代部分 Claude 调用，降低成本。主要挑战：远程监督会引入噪声（同一段落不一定真的表达了对应关系），需要用降噪策略（如多实例学习、置信度过滤）清理训练数据。当前建议以小规模人工验证集来评估自动标注质量后再决定是否大规模使用。D3. Think-on-Graph（ToG）论文Think-on-Graph: Deep and Responsible Reasoning of Large Language Model on Knowledge Graph来源ICLR 2024 · github.com/IDEA-FinAI/ToG核心范式：把 LLM 当作智能体，在图上做迭代束搜索（beam search）主动发现路径，而非穷举候选对。每跳分两步：关系探索：查询当前节点的所有出边候选关系类型，LLM 根据当前目标选出 top-N 个最有价值的关系类型。实体探索：对选中的关系类型查询候选尾实体，LLM 再剪枝选出最有价值的实体，作为下一跳的起点。用本项目的例子说明：起点：Risk-01（传感器漂移）&#10;第1跳关系探索：出边候选 [MITIGATED_BY, STATED_IN, PART_OF, RELATES_TO]&#10; LLM 选 MITIGATED_BY（与「发现管控链」目标最相关）&#10;第1跳实体探索：候选 [CM-03, CM-07, CM-12]&#10; LLM 选 CM-03（置信度最高）&#10;第2跳关系探索：从 CM-03 出发，候选 [VERIFIED_BY, IMPLEMENTED_IN, REPORTED_IN]&#10; LLM 选 VERIFIED_BY&#10;第2跳实体探索：候选 [T-12, T-15]&#10; LLM 选 T-12&#10;&#10;→ 发现路径：Risk-01 →[MITIGATED_BY]→ CM-03 →[VERIFIED_BY]→ T-12与遍历的区别：ToG 不是遍历整个图（复杂度 O(V+E)），每一跳只通过 Cypher 查询当前节点的直接邻居关系，再由 LLM 剪枝，实际遍历的节点数极少。对项目的核心价值：「主动发现追溯链中的缺失环节」。图里已有 Risk-01 → CM-03，ToG 可以主动发问「CM-03 应有 VERIFIED_BY 但图里没有，最可能的 Test 节点是哪个」——这既是候选对发现，也是一致性问题的直接检出。适合全量文件处理完后定期批量扫描图中的缺失环节。D4. KG Embedding + 链接预测核心思路：把图中所有节点和边压缩成低维向量，让向量空间的几何关系反映图的结构关系。训练完后，对任意节点对计算「它们之间存在某条边的概率」（链接预测），用于批量扫描图中所有缺失边。代表方法演进：TransE（2013）：若 (h, r, t) 是真实三元组，则 向量(h) + 向量(r) ≈ 向量(t)。给定 h 和 r，找使等式最成立的 t 即为链接预测结果。直觉简洁，对简单关系效果好。RotatE（2019）：把翻译操作推广到复数空间中的旋转，能同时处理对称、反对称、逆关系和组合关系，是目前工程性价比最高的 embedding 方法。LLM + KG Embedding 混合（2024）：用 LLM 的文本理解能力增强实体和关系的表示，弥补纯结构方法对文本语义利用不足的问题。与 Think-on-Graph 的区别：ToG 需要在线让 LLM 一步步探索，成本较高，适合针对特定节点的深度推理；KG Embedding 训练一次之后推断极快，适合全图批量扫描缺失边。对项目的价值与时机：阶段状态建议当前（379条边）图中边太少，embedding 学到的向量接近随机不可用，先积累高质量边全量处理后（预计数千条边）向量空间有足够约束，链接预测可用训练 RotatE，批量预测缺失边现在可做的准备—严格规范节点 type 字段和边的 relation 字段，确保数据干净— 报告结束 —
