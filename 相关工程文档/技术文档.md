# 医疗器械项目文档一致性审查系统 — 技术路线说明书

> 版本：v0.2 | 日期：2026-06-10 | 项目：PT9L 红外体温计 DHF 文档审查

---

## 一、我们要解决什么问题

### 1.1 背景

一款医疗器械从立项到上市，会产生大量过程文档——需求书、设计输入、风险评估、软件需求、验证计划、检测报告、评审记录等等。以 PT9L 红外体温计为例，全流程约 254 份文件（doc/xls/pdf），按 12 个 DHF 阶段组织。

这些文件之间并非孤立存在，它们有着复杂的内在关系：

- 设计输入必须覆盖需求书中的每一条要求
- 设计输入的指标不能低于需求书的要求
- 需求书的指标不能低于适用法规的要求
- 风险评估中识别的每一个风险，都必须在风险控制报告中被处理
- 每个风险控制措施都必须有测试验证其有效性
- 所有文件中出现的产品编号、项目号、版本号必须一致
- 评审签字人的姓名、部门、职务必须与项目组名单一致

目前，这些一致性检查完全依赖人工逐份翻阅、交叉比对。效率低、容易遗漏，尤其是跨多份文件的连锁矛盾更是难以人眼发现。

### 1.2 目标

建立一套自动化系统，能够：

1. 读入全部 254 份文件
2. 自动发现文件间的冲突、矛盾与遗漏
3. 输出一份审查报告，列出每一条问题及其精确的双向定位（哪个文件的哪一章/哪一行）

### 1.3 核心难点

**跨文件的语义对齐**——这是整个系统成败的关键。

举例：需求书里写"测量精度：±0.2℃"，检测报告里写"accuracy: ±0.3°C"，法规里写"Maximum permissible error shall not exceed ±0.3°C"。三者说的是同一件事，但文本完全不同——语言不同、术语不同、格式不同。

如果我们不能正确识别"它们说的是同一件事"，就不可能判断它们是否冲突。

传统的文本相似度（embedding cosine similarity）在这里很不可靠：措辞不同的同一参数相似度可能很低；措辞相近但实质不同的参数相似度反而可能很高。我们需要一种更可靠的对齐方法。

## 二、技术路线的核心思想

### 2.1 一句话概括

> 把每份文件中的事实性陈述，抽取并归一化为统一格式的"结构化断言"，然后通过结构化字段做精确匹配来实现跨文件对齐，最后在对齐结果上执行一致性规则检查。

### 2.2 类比理解

想象你雇了 100 个助理，让他们把 254 份文件里的每一条有用信息都抄到统一格式的索引卡片上：

然后把所有卡片按"主题+属性"分组放入抽屉。打开"测温精度/允许误差"这个抽屉，里面有来自不同文件的多张卡片——它们说的就是同一件事。然后比对数值：一致？矛盾？遗漏？

**这就是整个系统的核心思路。**

- "卡片"在系统中叫做 **Claim（归一化断言）**
- "不能做成卡片但包含重要信息的便签"叫做 **SemanticFragment（语义片段）**
- "按主题+属性分组"就是 **对齐（Alignment）**
- "比对数值"就是 **一致性检查（Consistency Check）**
- "抽屉柜"用 **知识图谱（Neo4j 图数据库）** 来存储

### 2.3 为什么选择知识图谱而非传统数据库

因为文件间的关系是**网状**的，不是线性或树状的：

- 一条需求可能对应多个设计输入
- 一个设计输入可能同时受多条法规约束
- 一个风险可能需要多个控制措施，每个措施需要不同的测试验证
- 一个人可能在多份文件中签字

图数据库天然适合表达和查询这种多对多的网状关系。更关键的是，很多检查规则本质上是"在图上找特定形状的路径"——比如"找所有没有下游验证的风险控制措施"，就是找"从 RiskControl 节点出发没有 VERIFIED_BY 出边"的情况。这在图数据库中一条查询即可表达。

## 三、整体流程设计

系统分为 5 个模块，按顺序串行执行：

### 模块一：格式转换

**输入**：254 个原始文件（doc/xls/pdf）

**输出**：254 个结构化 Markdown 文件

**做什么**：把二进制格式的文件转成 LLM 能阅读的文本格式，同时保留关键结构信息——标题层级、表格行列、页码、单元格坐标。

**为什么重要**：你的文件中大量关键参数存储在 Excel 表格的特定单元格中（如设计输入汇总表、需求清单）。如果转换时丢失了表格结构，后续抽取就会把数值和参数名搞混。

**工具选型**：
- Excel → pandas + openpyxl（精确控制每个单元格）
- Word → markitdown（微软开源，保留标题层级）
- PDF → Docling（IBM 开源，表格还原效果最好）

### 模块二：信息抽取

**输入**：254 个 Markdown 文件

**输出**：结构化 JSON（每个文件一份，包含从中抽出的所有节点和关系）

**做什么**：让 LLM 逐份阅读文件，按预定义的 schema 把里面的信息抽取成结构化数据。这是让 AI "制作索引卡片"的过程。

**关键设计——术语归一化表**：

为了让不同文件中措辞不同的同一概念被归为同一个 subject，我们给 LLM 提供一张术语表：

| 文件中可能出现的各种表述 | 统一标准词 |
|---|---|
| 测量精度、accuracy、允差、最大允许误差 | measurement_accuracy |
| 测温范围、测量范围、temperature range | measurement_range |
| 工作温度、使用环境温度、operating temp | operating_temperature |
| 电池寿命、battery life、使用次数 | battery_life |

这张表不需要人工穷举——先让 LLM 做一遍无约束抽取，收集所有 subject，再用 LLM 做聚类归一化，人工审核 10 分钟即可。之后的正式抽取按表执行。

**两遍抽取策略**：

- 第一遍：抽取节点的丰富属性（用 Pydantic 结构化输出）——Claim 的 5 个字段、Risk 的 7 个字段等
- 第二遍：抽取节点间的关系（用 LlamaIndex SchemaLLMPathExtractor）——谁引用谁、谁派生自谁

分两遍是因为三元组格式 (A, 关系, B) 存不下一个节点的多个属性字段。

### 模块二补充：Schema 详细定义

#### A. 节点类型完整定义（Pydantic Models）

```python
from pydantic import BaseModel
from typing import Optional, Literal

# ===== 层1：文档结构层（定位溯源）=====

class Document(BaseModel):
    """一份具体的文件"""
    doc_id: str                    # 唯一标识，如 "DHF-01-001"
    title: str                     # 文件标题
    doc_type: str                  # 文件类型：需求书/设计输入/风险报告/...
    dhf_stage: str                 # DHF阶段：01_立项/03_风险/04_设计输入/...
    version: Optional[str]         # 版本号
    filename: str                  # 原始文件名
    format: str                    # 原始格式：doc/xls/pdf
    path: str                      # 文件路径
    date: Optional[str]            # 文件日期
    lang: Optional[str]            # 语言：zh/en

class Section(BaseModel):
    """文件中的一个章节/段落/表格行"""
    section_id: str                # 唯一标识
    doc_id: str                    # 所属文件
    heading_path: str              # 层级路径，如 "第3章>3.2性能>表3-1>Row7"
    page: Optional[int]            # 页码
    order: int                     # 在文件中的出现顺序

# ===== 层2：标识与元数据层（确定性锚点）=====

class Product(BaseModel):
    """产品实体"""
    product_id: str                # 产品编号，如 "PT9L"
    model: Optional[str]           # 型号
    name: str                      # 产品名称
    region: Optional[str]          # 目标市场/地区

class Identifier(BaseModel):
    """各类标识号（做成独立节点以支持唯一性检查）"""
    id_type: Literal["产品编号", "项目号", "版本号", "需求编号", "设计输入编号", "风险编号", "测试编号"]
    value: str                     # 编号值

class Person(BaseModel):
    """人员"""
    name: str
    dept: Optional[str]            # 部门
    title: Optional[str]           # 职务/职称

# ===== 层3：领域实体层（业务语义）=====

class Requirement(BaseModel):
    """需求书中的一条需求条目"""
    req_id: str                    # 需求编号，如 "REQ-PERF-007"
    category: Literal["通用", "功能", "性能", "组件", "法规"]
    description: str               # 需求描述原文
    value: Optional[str]           # 量化值
    unit: Optional[str]            # 单位
    condition: Optional[str]       # 适用条件
    verification_method: Optional[str]  # 验证方法

class DesignInput(BaseModel):
    """设计输入条目"""
    di_id: str                     # 编号，如 "DI-P-012"
    category: Literal["通用", "功能", "性能", "组件", "法规"]
    description: str
    value: Optional[str]
    unit: Optional[str]
    condition: Optional[str]
    source_req_id: Optional[str]   # 来源需求编号（追溯用）

class Risk(BaseModel):
    """风险评估中的一条风险项"""
    risk_id: str                   # 如 "H-014"
    hazard: str                    # 危险源
    hazardous_situation: str       # 危险情况
    harm: str                      # 伤害
    severity: int                  # 严重度 1-5
    probability: str               # 概率 A-E
    risk_level: Literal["Acceptable", "ALARP", "Unacceptable"]
    phase: Optional[str]           # pre-mitigation / post-mitigation

class RiskControl(BaseModel):
    """风险控制措施"""
    measure: str                   # 措施描述
    type: Literal["降低可能性", "降低危害", "信息安全"]
    evidence_type: Optional[str]   # 证据类型：测试报告/分析/...

class Test(BaseModel):
    """一次具体的测试"""
    test_id: str
    item: str                      # 测试项目
    condition: Optional[str]       # 测试条件
    expected_value: Optional[str]  # 预期结果/通过标准
    actual_result: Optional[str]   # 实际结果
    pass_criteria: Optional[str]   # 判据

class TestReport(BaseModel):
    """测试报告"""
    report_id: str
    conclusion: Literal["PASS", "FAIL", "CONDITIONAL"]
    evidence_level: Optional[str]  # 证据等级

class Regulation(BaseModel):
    """法规/标准条款"""
    std_id: str                    # 标准号，如 "IEC 80601-2-56:2017"
    version: str                   # 版本
    clause: Optional[str]          # 条款号，如 "201.101"
    requirement_value: Optional[str]  # 法规要求的数值
    requirement_text: Optional[str]   # 法规要求的文字描述

class Function(BaseModel):
    """产品功能项"""
    name: str                      # 功能名称
    description: Optional[str]
    exists: bool = True            # 是否真实存在（用于串货检测）

class Component(BaseModel):
    """BOM零部件"""
    part_no: Optional[str]         # 物料编号
    name: str                      # 名称
    qty: Optional[str]             # 数量
    spec: Optional[str]            # 规格

class ReviewRecord(BaseModel):
    """评审记录"""
    review_id: str
    stage: str                     # 所属阶段
    date: Optional[str]
    conclusion: Optional[str]      # 评审结论

# ===== 层4：对齐与裁决层（系统核心+输出）=====

class Claim(BaseModel):
    """归一化事实断言——整个系统的对齐主干"""
    claim_id: str
    subject: str              # 标准化主题词（由术语归一化表约束）
    attribute: str            # 该主题的具体方面（允差/范围/阈值/实测值/判据...）
    value: Optional[str]      # 数值
    unit: Optional[str]       # 单位
    condition: Optional[str]  # 适用条件/前提
    raw_text: str             # 原文（用于人工回查和溯源展示）
    source_doc: str           # 来源文件
    source_section: str       # 来源章节（精确到行/单元格）

class Statement(BaseModel):
    """定性声明（Claim的弱化版，用于无法量化的Q&A式内容）"""
    standard_clause: Optional[str]   # 标准条款号，如 "ISO/TR 24971 A.2.1"
    question_summary: Optional[str]  # 问题摘要
    answer: str                      # 回答内容
    answer_type: Literal["yes", "no", "descriptive", "quantitative", "n_a"]
    source_doc: str
    source_section: str

class SemanticFragment(BaseModel):
    """语义片段——无法结构化为Claim但可能包含审查相关信息的描述性段落"""
    fragment_id: str
    fragment_type: Literal[
        "design_rationale",      # 设计理由/决策（如"选NTC而非红外阵列的原因"）
        "working_principle",     # 工作原理描述（如"算法通过环境温度补偿..."）
        "constraint_statement",  # 隐含约束/范围限制（如"仅在XX条件下有效"）
        "behavioral_spec",       # 行为描述（如"当温度超过42℃时显示ERR"）
        "open_issue",            # 未关闭问题（如"待确认是否需要增加自检"）
        "scope_limitation",      # 适用范围限制（如"本方案不适用于耳温模式"）
        "assumption",            # 前提假设（如"假定环境温度变化率＜2℃/min"）
    ]
    content: str                 # 原文内容（完整保留，不做任何压缩）
    topic_tags: list[str]        # 主题标签（如 ["温度补偿", "工作范围", "算法"]）
    related_subjects: list[str]  # 关联的 Claim subject（如 ["operating_temperature"]）
    source_doc: str
    source_section: str
```

#### B. 边（关系）类型完整定义

**抽取阶段产生的边（由 LLM 从文件中识别）：**

| 关系类型 | 起点 → 终点 | 边属性 | 语义说明 |
|----------|-------------|--------|----------|
| `PART_OF` | Section → Document | | 章节属于文件 |
| `STATED_IN` | Claim/Risk/Requirement… → Section | span(原文片段) | 实体出现在该章节中 |
| `DECLARES` | Document → Identifier/Product/Person | role, dept, title, value, name_as_stated | 文件声称/提及该实体 |
| `DERIVES_FROM` | DesignInput → Requirement | source_ref | 设计输入来源于该需求 |
| `MUST_BE_GEQ` | DesignInput/Claim → Requirement/Regulation | direction | 数值约束：不得低于 |
| `CONSTRAINED_BY` | Requirement → Regulation | | 需求受法规约束 |
| `MITIGATED_BY` | Risk → RiskControl | | 风险被该措施控制 |
| `VERIFIED_BY` | RiskControl/DesignInput → Test | | 被该测试验证 |
| `REPORTED_IN` | Test → TestReport | | 测试结果记录在该报告中 |
| `ADDRESSED_IN` | Risk → Document | | 风险在该文件中被处理 |
| `SIGNED` | Person → Document/ReviewRecord | role(编写人/审批人/评审员) | 人员签署了该文件 |
| `IMPLEMENTED_IN` | Function → Document | | 功能在该文件中被实现/描述 |
| `REFERENCES` | Document → Document | ref_type(引用/参考/来源) | 文件间引用关系 |
| `RELATES_TO` | SemanticFragment → Claim | subject_overlap(共享subject列表) | 语义片段与结构化Claim的主题关联 |
| `POTENTIALLY_CONFLICTS` | SemanticFragment ↔ Claim / SemanticFragment ↔ SemanticFragment | conflict_type, explanation, severity, confidence | LLM判定的潜在逻辑矛盾（语义级检查输出） |

**推理阶段产生的边（由对齐引擎和检查引擎计算后写入）：**

| 关系类型 | 起点 → 终点 | 边属性 | 语义说明 |
|----------|-------------|--------|----------|
| `CORRESPONDS_TO` | Claim ↔ Claim | relation(equal/geq/lt/sub_allocation/condition_mismatch), confidence, method | 两个 Claim 说的是同一件事 |
| `CONFLICTS_WITH` | Claim ↔ Claim / Identifier ↔ Identifier | reason, severity, check_type | 检出的冲突（系统最终输出） |

#### C. LlamaIndex SchemaLLMPathExtractor 完整配置

```python
from typing import Literal
from llama_index.core.indices.property_graph import SchemaLLMPathExtractor

# 允许的节点类型
entities = Literal[

    "Requirement", "DesignInput", "Claim", "Risk", "RiskControl",
    "Test", "TestReport", "Regulation", "Function", "Component",
    "ReviewRecord", "Statement", "SemanticFragment",
]

# 允许的关系类型
relations = Literal[
    "PART_OF", "STATED_IN", "DECLARES", "DERIVES_FROM", "MUST_BE_GEQ",

    "ADDRESSED_IN", "SIGNED", "IMPLEMENTED_IN", "REFERENCES", "RELATES_TO",
]

# 合法三元组白名单（不在此列表中的抽取结果被丢弃）
validation_schema = [
    ("Section", "PART_OF", "Document"),
    ("Claim", "STATED_IN", "Section"),
    ("Statement", "STATED_IN", "Section"),
    ("Requirement", "STATED_IN", "Section"),
    ("Risk", "STATED_IN", "Section"),
    ("Test", "STATED_IN", "Section"),
    ("Document", "DECLARES", "Identifier"),
    ("Document", "DECLARES", "Product"),
    ("Document", "DECLARES", "Person"),
    ("DesignInput", "DERIVES_FROM", "Requirement"),
    ("DesignInput", "MUST_BE_GEQ", "Requirement"),
    ("Claim", "MUST_BE_GEQ", "Regulation"),
    ("Requirement", "CONSTRAINED_BY", "Regulation"),
    ("Risk", "MITIGATED_BY", "RiskControl"),
    ("RiskControl", "VERIFIED_BY", "Test"),
    ("DesignInput", "VERIFIED_BY", "Test"),
    ("Test", "REPORTED_IN", "TestReport"),
    ("Risk", "ADDRESSED_IN", "Document"),
    ("Person", "SIGNED", "Document"),
    ("Person", "SIGNED", "ReviewRecord"),
    ("Function", "IMPLEMENTED_IN", "Document"),
    ("Document", "REFERENCES", "Document"),
    ("SemanticFragment", "STATED_IN", "Section"),
    ("SemanticFragment", "RELATES_TO", "Claim"),
]

kg_extractor = SchemaLLMPathExtractor(
    llm=llm,
    possible_entities=entities,
    possible_relations=relations,
    kg_validation_schema=validation_schema,
    strict=True,  # 不合法的三元组直接丢弃
)
```

#### D. 术语归一化表（示例，完整版约 50-80 项）

| 文档中可能出现的表述 | 标准 subject 词 | 属性方向 |
|---------------------|----------------|----------|
| 测量精度/accuracy/允差/最大允许误差/maximum permissible error | measurement_accuracy | smaller_is_better |
| 测温范围/测量范围/temperature range/measuring range | measurement_range | wider_is_better |
| 工作温度/使用环境温度/operating temperature/环境温度 | operating_temperature | wider_is_better |
| 电池寿命/battery life/使用次数/battery capacity | battery_life | larger_is_better |
| 响应时间/response time/测量时间/measurement time | response_time | smaller_is_better |
| 分辨率/resolution/显示精度/display resolution | display_resolution | smaller_is_better |
| 重复性/repeatability/重复测量偏差 | repeatability | smaller_is_better |
| 报警阈值/fever alarm/发热报警温度 | fever_alarm_threshold | exact_match |
| 产品重量/weight/质量 | product_weight | exact_match |
| 产品尺寸/dimensions/外形尺寸 | product_dimensions | exact_match |
| 防水等级/IP rating/ingress protection | ip_rating | exact_match |
| 显示位数/display digits | display_digits | exact_match |
| 存储温度/storage temperature | storage_temperature | wider_is_better |
| 使用寿命/expected service life/产品寿命 | service_life | larger_is_better |
| 噪声/noise level/声压级 | noise_level | smaller_is_better |

**术语表的生成流程**：
1. 对全部文档做一遍无约束抽取（subject 字段自由填写）
2. 收集全部 unique subject 值（预计 300-500 个）
3. 用 LLM 做聚类归一化（"将同义表述归为一组，每组指定标准英文 key"）
4. 人工审核聚类结果（约 10 分钟）
5. 生成最终术语表，存入 config/terminology.yaml

#### E. Neo4j 数据库约束与索引

```cypher
-- 唯一性约束（防止重复创建节点）
```

### 模块四：对齐引擎

**输入**：图中所有 Claim 节点（约 3000 个）+ 所有 SemanticFragment 节点（约 200-400 个）

**输出**：Claim 之间的 CORRESPONDS_TO 边 + SemanticFragment 与 Claim/Fragment 之间的 POTENTIALLY_CONFLICTS 边

**做什么**：
1. 确定哪些来自不同文件的 Claim 说的是同一件事（结构化对齐）
2. 检测 SemanticFragment 中的隐含约束是否与已有 Claim 的声称矛盾（语义级对齐）

**为什么这一步最难**：3000 个 Claim 两两比较是 450 万对，每对都调 LLM 不现实（耗时+成本）。必须先大幅缩小候选范围。

**解决方案——分层 Blocking（候选筛选）**：

我们设计了 4 个并行通道来生成候选对，每个通道利用不同的信号：

1. **ID 锚点通道**：如果两个 Claim 的源文件都引用了同一个编号（如 REQ-PERF-007），且 subject 相同，则它们大概率说的是同一件事。精确率 >90%。

2. **Subject 匹配通道**：subject 字段相同的 Claim 归为一组，组内两两配对。这是主要的候选来源。

3. **本体约束剪枝**：并非所有文件都需要互查。利用 DHF 流程知识（如"需求书只和设计输入/验证计划对应"），剪掉不可能对应的跨阶段对，减少 40% 候选量。

4. **Embedding 兜底**：对前三个通道都没覆盖到的孤立 Claim，用向量相似度找最近邻，作为补充。

4 个通道合并去重后，约 2000 对候选——从 450 万压缩到 2000，缩减 99.96%。

然后对这 2000 对调 LLM 做精确判断："这两条断言是否说同一件事？数值关系是什么（相等/满足/不满足）？"

### 模块四补充：对齐引擎完整算法

#### A. Blocking 详细实现

**通道 A — ID 锚点（Cypher 实现）：**

```cypher
MATCH (c1:Claim)-[:STATED_IN]->(:Section)-[:PART_OF]->(d1:Document)
      -[:REFERENCES]->(shared:Document)<-[:REFERENCES]-
      (d2:Document)<-[:PART_OF]-(:Section)<-[:STATED_IN]-(c2:Claim)
WHERE c1.subject = c2.subject AND c1.claim_id < c2.claim_id
      AND d1.doc_id <> d2.doc_id
RETURN c1.claim_id, c2.claim_id AS candidate_pair
```

**通道 B — Subject 精确分组（Python 实现）：**

```python
from collections import defaultdict
from itertools import combinations

def blocking_by_subject(claims: list[Claim]) -> list[tuple]:
    groups = defaultdict(list)
    for c in claims:
        groups[c.subject].append(c)
    
    candidates = []
    for subject, group in groups.items():
        for ci, cj in combinations(group, 2):
            if ci.source_doc != cj.source_doc:  # 排除同文件内的对
                candidates.append((ci.claim_id, cj.claim_id))
    return candidates
```

**通道 C — 本体约束剪枝（过滤逻辑）：**

```python
# 阶段对应矩阵（只有 True 的组合才保留为候选）
STAGE_MATRIX = {
    ("01_立项", "04_设计输入"): True,
    ("01_立项", "08_T1"): True,
    ("04_设计输入", "07_软件"): True,
    ("04_设计输入", "08_T1"): True,
    ("08_T1_计划", "08_T1_报告"): True,
    ("03_风险_02", "03_风险_03"): True,
    ("04_设计输入", "09_设计输出"): True,
    ("07_软件", "08_T1"): True,
}

def prune_by_ontology(candidates, claims_dict, docs_dict):
    """剪枝：只保留阶段对应矩阵中允许的对"""
    pruned = []
    for (id1, id2) in candidates:
        stage1 = docs_dict[claims_dict[id1].source_doc].dhf_stage
        stage2 = docs_dict[claims_dict[id2].source_doc].dhf_stage
        pair = tuple(sorted([stage1, stage2]))
        if STAGE_MATRIX.get(pair, False):
            pruned.append((id1, id2))
    return pruned
```

**通道 D — Embedding 兜底：**

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('BAAI/bge-m3')

def blocking_by_embedding(orphan_claims: list[Claim], all_claims: list[Claim], top_k=3):
    """对未被 A/B 覆盖的孤立 Claim，用向量近邻找候选"""
    orphan_texts = [c.raw_text for c in orphan_claims]
    all_texts = [c.raw_text for c in all_claims]
    
    orphan_embs = model.encode(orphan_texts)
    all_embs = model.encode(all_texts)
    
    candidates = []
    for i, emb in enumerate(orphan_embs):
        sims = np.dot(all_embs, emb)
        top_indices = np.argsort(sims)[-top_k:]
        for j in top_indices:
            if all_claims[j].source_doc != orphan_claims[i].source_doc:
                candidates.append((orphan_claims[i].claim_id, all_claims[j].claim_id))
    return candidates
```

#### D. SemanticFragment 对齐——语义级矛盾检测

Claim 对齐处理的是**能结构化的内容**之间的数值比较。但很多重要信息藏在描述性文字中，无法变成 Claim。SemanticFragment 对齐解决的是：**描述性文字与结构化 Claim 之间、以及描述性文字相互之间的逻辑矛盾检测**。

**核心问题**：SemanticFragment 是原文段落，没有 value/unit 等字段，不能用数值比较。必须用 LLM 做逻辑推理级别的判断。

**Blocking 策略（三层漏斗）**：

```python
from itertools import product as cartesian_product

def blocking_fragments(fragments: list, claims: list, stage_matrix: dict) -> list[tuple]:
    """
    三层漏斗筛选 SemanticFragment 候选对：
    层1: related_subjects 交集匹配（Fragment vs Claim）
    层2: topic_tags 语义重叠（Fragment vs Fragment）
    层3: 来源文件阶段约束（剪枝）
    """
    candidates = []
    
    # === 层1: Fragment vs Claim（related_subjects 匹配）===
    for frag in fragments:
        for claim in claims:
            if claim.subject in frag.related_subjects:
                candidates.append(("frag_vs_claim", frag.fragment_id, claim.claim_id))
    
    # === 层2: Fragment vs Fragment（topic_tags 语义重叠）===
    for i, f1 in enumerate(fragments):
        for f2 in fragments[i+1:]:
            if f1.source_doc == f2.source_doc:
                continue
            shared_tags = set(f1.topic_tags) & set(f2.topic_tags)
            if shared_tags:
                candidates.append(("frag_vs_frag", f1.fragment_id, f2.fragment_id))
    
    # === 层3: 阶段约束剪枝 ===
    pruned = []
    for pair_type, id1, id2 in candidates:
        stage1 = get_stage(id1)
        stage2 = get_stage(id2)
        pair_key = tuple(sorted([stage1, stage2]))
        if stage_matrix.get(pair_key, False):
            pruned.append((pair_type, id1, id2))
    
    return pruned
```

## 四、检查引擎的规则体系

### 4.1 规则从哪来？

这是很多人的第一个疑问："你的规则库是人工写的吗？会不会太依赖人工经验？"

答案是：**绝大部分规则不来自人工经验，而是从 schema 设计和 DHF 流程逻辑自动推导的。** 来源分三层：

**第一层：Schema 内生规则（定义了 schema 就自动存在）**

当我们定义了"Identifier 节点是唯一的、多个文件连向同一个节点"这个结构，就隐含了"同一编号在各文件中的值必须相同"这条规则。不需要人说"去检查产品编号"——系统会自动检查所有 Identifier 类型的节点。

类似地：
- 同一 Person 节点的属性（部门/职务）各处应一致 → 自动检查
- CORRESPONDS_TO 边声明 relation=equal 的两端值必须相等 → 自动检查

**第二层：本体完整性规则（从 DHF/ISO 13485 流程推导，一次性定义）**

医疗器械设计控制流程对文件间的追溯关系有明确要求。这些要求可以编码为图的完整性约束：

- 每个 Requirement 必须有至少一个 DesignInput 派生自它（追溯覆盖）
- 每个 Risk 必须有 RiskControl 关联（风险必须被控制）
- 每个 RiskControl 必须有 Test 验证（控制措施必须被验证）
- 每个 DesignInput 必须有 Test 验证（设计必须被验证）

这些规则对所有医疗器械项目通用，定义一次永久复用。

**第三层：领域约束（少量，需领域知识）**

- 属性方向表（精度越小越好 vs 范围越宽越好）
- 产品功能白名单（红外温度计不该有"语音播报"）
- 法规版本有效性表

这些也是一次性定义、按产品线复用的。

**口述经验（如 20260603 讨论.docx）的真正定位**：不参与运行时的检查逻辑，而是作为验证集——用来检验上述三层规则是否能覆盖人工审查员关注的点。如果有遗漏，说明 schema 或规则需要补充。

### 4.2 七类检查详解

我们把所有检查归为 7 类：

**① 字段一致性**

检查内容：产品编号、项目号、版本号、产品名称在所有文件中是否一致。

检查方式：找同一个 Identifier/Product 节点被多个文件 DECLARES 时，各处的取值是否完全相等。

典型发现：立项批准书写"PT9L-001"，检测报告写"PT9L-01"——少了个零。

**② 人员一致性**

检查内容：同一人在不同文件中的部门、职务是否一致；评审签字人是否在项目组名单中。

检查方式：对 Person 节点，比较其在不同文件中被声称的属性（dept/title）。

典型发现：评审记录中"王五/生产部/工程师"，但项目组名单中"王五/研发部/高级工程师"。

**③ 追溯与不退化（最复杂的一类）**

检查内容：
- 需求是否被设计输入完整覆盖
- 设计输入的指标是否不低于需求
- 对齐后的 Claim 数值是否一致
- 验证范围是否覆盖需求范围
- 风险是否全部被处理
- 风控措施是否全部被验证

检查方式：图的追溯路径完整性 + 数值约束满足性。

典型发现：验证计划的 pass criteria 是 ±0.2℃，但检测报告的判据变成了 ±0.3℃——判据被偷偷放宽了。

**④ 法规符合性**

检查内容：法规清单是否被需求完整覆盖；需求值是否不低于法规要求；引用的标准版本是否为最新。

检查方式：Requirement → CONSTRAINED_BY → Regulation 路径的完整性和数值比较。

**⑤ 完整性/遗漏**

检查内容：BOM 是否有空项；每个类别的设计输入是否都有对应测试；引用的文件是否存在。

检查方式：节点属性非空检查 + 按类别统计覆盖率。

**⑥ 错配/串货**

检查内容：是否出现了不属于本产品的功能描述（复制粘贴残留）；是否出现了其他产品的编号。

检查方式：建立功能白名单，检查超出白名单的功能出现；全文扫描非当前产品编号的出现。

典型发现：软件质量策划中提到"语音播报功能"，但 PT9L 红外温度计并没有这个功能——大概率是从另一个产品复制模板时没改干净。

**⑦ 语义片段矛盾（描述性文字中的隐含冲突）**

检查内容：描述性文字（工作原理、设计决策、隐含约束等）是否与结构化声明（Claim）或其他描述性文字存在逻辑矛盾。

检查方式：通过 SemanticFragment 的 `related_subjects` 与 Claim 的 `subject` 匹配建立候选对，再用 LLM-as-Judge 做逻辑推理判断是否存在冲突。

典型发现：软件方案中描述"温度补偿算法有效范围 16-35℃"，但设计输入声称"工作温度 10-40℃"——算法在 10-16℃ 和 35-40℃ 范围内无法保证精度，存在覆盖缺口。

### 4.3 检查的执行方式

不是人手动触发，而是**全自动批量执行**：

系统启动后，自动依次执行全部 22 条规则（每条规则是一个图查询模板），收集所有违规结果，按严重度排序，生成审查报告。整个过程无需人工干预。

审查报告中每条发现都带有精确的双向定位（文件A的哪一章 vs 文件B的哪一章），审查员可以直接跳转到原文核实。

### 4.4 完整规则库（22 条 Cypher 查询）

#### 规则组 A：字段一致性（2 条）

**A1 — 标识符唯一性** [严重度: HIGH]

```cypher
MATCH (d1:Document)-[r1:DECLARES]->(id:Identifier)<-[r2:DECLARES]-(d2:Document)
WHERE d1.doc_id < d2.doc_id AND r1.value <> r2.value
RETURN id.id_type AS 标识类型, id.value AS 标识,
       d1.title AS 文件1, r1.value AS 值1,
       d2.title AS 文件2, r2.value AS 值2
```

**A2 — 产品名称一致性** [严重度: MEDIUM]

```cypher
MATCH (d:Document)-[r:DECLARES]->(p:Product)
WITH p, COLLECT(DISTINCT r.name_as_stated) AS names
WHERE SIZE(names) > 1
RETURN p.product_id, names AS 各文件中的产品名称
```

#### 规则组 B：人员一致性（2 条）

**B1 — 部门/职务一致性** [严重度: LOW-MEDIUM]

```cypher
MATCH (d:Document)-[r:DECLARES]->(p:Person)
WITH p, COLLECT({doc: d.title, dept: r.dept, title: r.title}) AS mentions
WITH p, mentions, [m IN mentions | m.dept] AS depts
WHERE SIZE(apoc.coll.toSet(depts)) > 1
RETURN p.name AS 人员, mentions AS 各文件记录
```

**B2 — 签字人存在于项目组** [严重度: MEDIUM]

```cypher
MATCH (p:Person)-[:SIGNED]->(rr:ReviewRecord)
WHERE NOT EXISTS {
  MATCH (:Document {doc_type:"项目组成员名单"})-[:DECLARES]->(p)
}
RETURN p.name AS 签字人不在名单中, rr.review_id AS 评审记录
```

#### 规则组 C：追溯与不退化（7 条）

**C1 — 需求追溯完整性** [严重度: HIGH]

```cypher
MATCH (req:Requirement)
WHERE NOT EXISTS { MATCH (:DesignInput)-[:DERIVES_FROM]->(req) }
RETURN req.req_id AS 需求编号, req.description AS 未被覆盖的需求
```

**C2 — 设计输入不低于需求** [严重度: HIGH]

```cypher
MATCH (di:DesignInput)-[:DERIVES_FROM]->(req:Requirement)
MATCH (meta:MetaAttribute {subject: di.subject})
WHERE di.value IS NOT NULL AND req.value IS NOT NULL
WITH di, req, meta, toFloat(di.value) AS di_val, toFloat(req.value) AS req_val
WHERE (meta.direction = "smaller_is_better" AND di_val > req_val)
   OR (meta.direction = "larger_is_better" AND di_val < req_val)
RETURN di.di_id, di.value AS 设计输入值, req.req_id, req.value AS 需求值
```

**C3 — Claim 数值一致性（核心规则）** [严重度: HIGH]

```cypher
MATCH (c1:Claim)-[r:CORRESPONDS_TO]->(c2:Claim)
WHERE r.relation = "equal" AND c1.value <> c2.value
MATCH (c1)-[:STATED_IN]->(s1:Section)-[:PART_OF]->(d1:Document)
MATCH (c2)-[:STATED_IN]->(s2:Section)-[:PART_OF]->(d2:Document)
RETURN c1.subject AS 主题, c1.attribute AS 属性,
       d1.title AS 文件1, s1.heading_path AS 位置1, c1.value AS 值1,
       d2.title AS 文件2, s2.heading_path AS 位置2, c2.value AS 值2
```

**C4 — 条件/范围覆盖性** [严重度: MEDIUM]

```cypher
MATCH (c1:Claim)-[r:CORRESPONDS_TO]->(c2:Claim)
WHERE c1.condition IS NOT NULL AND c2.condition IS NOT NULL
  AND c1.condition <> c2.condition
MATCH (c1)-[:STATED_IN]->(s1:Section)-[:PART_OF]->(d1:Document)
MATCH (c2)-[:STATED_IN]->(s2:Section)-[:PART_OF]->(d2:Document)
WHERE d1.dhf_stage IN ["01_立项", "04_设计输入"]
  AND d2.dhf_stage IN ["08_T1"]
RETURN c1.subject, c1.condition AS 需求范围, c2.condition AS 验证范围,
       d1.title AS 需求文件, d2.title AS 验证文件
```

**C5 — 风险全覆盖（02→03）** [严重度: CRITICAL]

```cypher
MATCH (risk:Risk)-[:STATED_IN]->(:Section)-[:PART_OF]->(d:Document)
WHERE d.title CONTAINS "02" AND d.dhf_stage = "03_风险"
AND NOT EXISTS {
  MATCH (risk)-[:ADDRESSED_IN]->(d2:Document) WHERE d2.title CONTAINS "03"
}
RETURN risk.risk_id AS 风险编号, risk.hazard AS 危险源
```

**C6 — 风控措施验证闭环** [严重度: HIGH]

```cypher
MATCH (risk:Risk)-[:MITIGATED_BY]->(rc:RiskControl)
WHERE NOT EXISTS { MATCH (rc)-[:VERIFIED_BY]->(:Test) }
RETURN risk.risk_id AS 风险, rc.measure AS 缺少验证的控制措施
```

**C7 — 设计输入验证覆盖** [严重度: MEDIUM]

```cypher
MATCH (di:DesignInput)
WHERE NOT EXISTS { MATCH (di)-[:VERIFIED_BY]->(:Test) }
RETURN di.di_id AS 设计输入编号, di.description AS 未安排验证的设计输入
```

#### 规则组 D：法规符合性（3 条）

**D1 — 法规覆盖完整性** [严重度: HIGH]

```cypher
MATCH (reg:Regulation)
WHERE NOT EXISTS { MATCH (:Requirement)-[:CONSTRAINED_BY]->(reg) }
RETURN reg.std_id AS 标准号, reg.clause AS 条款
```

**D2 — 需求不低于法规** [严重度: CRITICAL]

```cypher
MATCH (req:Requirement)-[:CONSTRAINED_BY]->(reg:Regulation)
MATCH (meta:MetaAttribute {subject: req.subject})
WHERE req.value IS NOT NULL AND reg.requirement_value IS NOT NULL
WITH req, reg, meta, toFloat(req.value) AS req_val, toFloat(reg.requirement_value) AS reg_val
WHERE (meta.direction = "smaller_is_better" AND req_val > reg_val)
   OR (meta.direction = "larger_is_better" AND req_val < reg_val)
RETURN req.req_id, req.value AS 需求值, reg.std_id, reg.requirement_value AS 法规值
```

**D3 — 法规版本时效性** [严重度: MEDIUM]

```cypher
MATCH (reg:Regulation)
MATCH (latest:RegulationLatest {std_id: reg.std_id})
WHERE reg.version <> latest.current_version
RETURN reg.std_id, reg.version AS 引用版本, latest.current_version AS 最新版本
```

#### 规则组 E：完整性/遗漏（3 条）

**E1 — BOM 无空项** [严重度: LOW]

```cypher
MATCH (comp:Component)-[:STATED_IN]->(s:Section)-[:PART_OF]->(d:Document)
WHERE comp.part_no IS NULL OR comp.name IS NULL OR comp.qty IS NULL
RETURN d.title AS 文件, s.heading_path AS 位置, comp.name AS 组件
```

**E2 — 测试条目按类别完整** [严重度: HIGH]

```cypher
MATCH (di:DesignInput)
WITH di.category AS cat, COUNT(di) AS total
OPTIONAL MATCH (di2:DesignInput {category: cat})-[:VERIFIED_BY]->(t:Test)
WITH cat, total, COUNT(DISTINCT t) AS test_count
WHERE test_count = 0
RETURN cat AS 完全未验证的类别, total AS 该类别设计输入数
```

**E3 — 引用文件存在性** [严重度: MEDIUM]

```cypher
MATCH (d1:Document)-[r:REFERENCES]->(d2:Document)
WHERE d2.filename IS NULL
RETURN d1.title AS 引用方, r.ref_type AS 引用类型, "引用目标不存在" AS 问题
```

#### 规则组 F：错配/串货（2 条）

**F1 — 功能白名单校验** [严重度: HIGH]

```cypher
MATCH (func:Function)-[:STATED_IN]->(:Section)-[:PART_OF]->(d:Document)
WHERE d.dhf_stage = "01_立项"
WITH COLLECT(DISTINCT func.name) AS whitelist
MATCH (func2:Function)-[:STATED_IN]->(s:Section)-[:PART_OF]->(d2:Document)
WHERE d2.dhf_stage <> "01_立项" AND NOT func2.name IN whitelist
RETURN func2.name AS 可疑功能, d2.title AS 出现文件, s.heading_path AS 位置
```

**F2 — 产品型号串档** [严重度: HIGH]

```cypher
MATCH (prod:Product)
WITH prod.product_id AS current_id
MATCH (c:Claim)
WHERE ANY(other_id IN ["PT5", "PT7", "PT8"] WHERE c.raw_text CONTAINS other_id)
  AND NOT c.raw_text CONTAINS current_id
MATCH (c)-[:STATED_IN]->(s:Section)-[:PART_OF]->(d:Document)
RETURN d.title AS 文件, s.heading_path AS 位置, c.raw_text AS 疑似串档内容
```

#### 规则组 G：语义片段矛盾检测（3 条）

**G1 — Fragment vs Claim 潜在冲突** [严重度: HIGH]

```cypher
MATCH (f:SemanticFragment)-[r:POTENTIALLY_CONFLICTS]->(c:Claim)
WHERE r.confidence >= 0.7
MATCH (f)-[:STATED_IN]->(s1:Section)-[:PART_OF]->(d1:Document)
MATCH (c)-[:STATED_IN]->(s2:Section)-[:PART_OF]->(d2:Document)
RETURN r.conflict_type AS 冲突类型, r.severity AS 严重度,
       d1.title AS 片段来源文件, s1.heading_path AS 片段位置,
       f.fragment_type AS 片段类型, LEFT(f.content, 80) AS 片段摘要,
       d2.title AS 断言来源文件, s2.heading_path AS 断言位置,
       c.subject AS 断言主题, c.value + c.unit AS 断言值,
       r.explanation AS 矛盾说明
ORDER BY r.severity, r.confidence DESC
```

**G2 — Fragment vs Fragment 潜在冲突** [严重度: MEDIUM-HIGH]

```cypher
MATCH (f1:SemanticFragment)-[r:POTENTIALLY_CONFLICTS]->(f2:SemanticFragment)
WHERE r.confidence >= 0.7
MATCH (f1)-[:STATED_IN]->(s1:Section)-[:PART_OF]->(d1:Document)
MATCH (f2)-[:STATED_IN]->(s2:Section)-[:PART_OF]->(d2:Document)
RETURN r.conflict_type AS 冲突类型, r.severity AS 严重度,
       d1.title AS 文件1, s1.heading_path AS 位置1,
       f1.fragment_type AS 类型1, LEFT(f1.content, 60) AS 摘要1,
       d2.title AS 文件2, s2.heading_path AS 位置2,
       f2.fragment_type AS 类型2, LEFT(f2.content, 60) AS 摘要2,
       r.explanation AS 矛盾说明
ORDER BY r.severity, r.confidence DESC
```

**G3 — 孤立 Section 检测（完全不透明区域标记）** [严重度: INFO]

```cypher
MATCH (s:Section)-[:PART_OF]->(d:Document)
WHERE NOT EXISTS { MATCH (:Claim)-[:STATED_IN]->(s) }
  AND NOT EXISTS { MATCH (:SemanticFragment)-[:STATED_IN]->(s) }
  AND NOT EXISTS { MATCH (:Statement)-[:STATED_IN]->(s) }
  AND NOT EXISTS { MATCH (:Risk)-[:STATED_IN]->(s) }
  AND NOT EXISTS { MATCH (:Requirement)-[:STATED_IN]->(s) }
RETURN d.title AS 文件, s.heading_path AS 位置, 
       "该章节无任何节点指向，内容对系统不透明" AS 说明
ORDER BY d.dhf_stage, s.order
```

### 4.5 检查引擎执行框架

```python
from dataclasses import dataclass
from enum import Enum

class Severity(Enum):
    CRITICAL = 1
    HIGH = 2
    MEDIUM = 3
    LOW = 4

@dataclass
class CheckRule:
    rule_id: str              # 如 "C3"
    name: str                 # 如 "Claim数值一致性"
    check_type: str           # 如 "追溯与不退化"
    description: str
    severity: Severity
    cypher: str               # 完整 Cypher 查询
    message_template: str     # 输出消息模板（用查询结果填充）

class CheckEngine:
    def __init__(self, neo4j_driver):
        self.driver = neo4j_driver
        self.rules: list[CheckRule] = self._load_all_rules()

    def run_all(self) -> list[dict]:
        """批量执行全部 22 条规则，返回问题清单"""
        findings = []
        with self.driver.session() as session:
            for rule in self.rules:
                results = session.run(rule.cypher)
                for record in results:
                    findings.append({
                        "rule_id": rule.rule_id,
                        "rule_name": rule.name,
                        "check_type": rule.check_type,
                        "severity": rule.severity.name,
                        "message": rule.message_template.format(**dict(record)),
                        "raw_data": dict(record),
                    })
        findings.sort(key=lambda x: Severity[x["severity"]].value)
        return findings
```

## 五、关于候选技术框架的评估

在立项调研中，我们考察了以下框架：

### 5.1 GraphRAG（Microsoft）

**是什么**：把文档构建成知识图谱，然后用图增强的 RAG 来回答问题。擅长"全局主题归纳"。

**为什么不适合**：GraphRAG 是被动问答系统——你问一个问题，它找答案。但我们需要的是主动审计——系统自己发现问题。GraphRAG 的开放式 schema（自动抽取通用实体/关系）也不够精确，容易漏掉我们需要的领域特定关系。

**结论**：不采用作为主链路。可作为辅助的问答接口供审查员手动查询。

### 5.2 Graphiti（Zep）

**是什么**：为 AI Agent 设计的时序知识图谱，强调增量更新和时间推理。

**为什么不适合**：我们的文档是静态归档文件，不需要时序记忆能力。Graphiti 的核心卖点（双时态边、实时事件融入）在我们场景中毫无用武之地，反而增加复杂度。

**结论**：不采用。

### 5.3 Cognee

**是什么**：灵活的"认知记忆层"框架，支持自定义本体和 pipeline 编排。

**为什么有犹豫**：定位偏向 Agent Memory，引导你走"Agent 对话记忆"范式，与我们的批处理审计范式不完全匹配。但它的 pipeline 编排能力不错。

**结论**：不作为主选。如果后续 LlamaIndex 在 pipeline 灵活度上遇到瓶颈，可考虑替换。

### 5.4 DeepWiki（Karpathy）

**是什么**：Karpathy 推出的 DeepWiki 能自动为代码仓库/文档集合生成结构化的 Wiki 页面，用 LLM 阅读全部内容后生成有组织的知识概览，配合对话式问答接口。本质是"LLM 阅读全文 → 生成结构化摘要 → 基于摘要做问答"。

**为什么不适合**：

1. **设计目标不同**：DeepWiki 的目标是"帮人快速理解一个项目"，输出的是 Wiki 式的知识概览和问答。我们的目标是"自动发现文件间的数值矛盾和逻辑遗漏"——这不是一个"理解"问题，而是一个"全量比对"问题。
2. **无法做精确数值比较**：DeepWiki 生成的是自然语言摘要。当需求书写"±0.2℃"、检测报告写"±0.3℃"时，Wiki 摘要可能会写"精度约为 0.2-0.3℃"——把冲突糊弄过去了。我们需要的是保留精确数值并做结构化比较。
3. **缺乏对齐机制**：DeepWiki 不会建立"文件A的第3行和文件B的第12行说的是同一件事"这种显式映射。它只是把信息重新组织成 Wiki 页面，跨文件的对应关系是隐式的、不可追溯的。
4. **无法主动报冲突**：DeepWiki 是被动的知识展示工具——你不问它就不说。而我们需要系统主动扫描全部参数对、逐一比对、批量报出所有问题。
5. **无法溯源到原文精确位置**：审查员需要"点击即跳转到原文具体行/单元格"的能力。Wiki 摘要丢失了这种精确定位。

**简单对比**：

| | DeepWiki | 我们的系统 |
|---|---|---|
| 输出 | 结构化 Wiki + 问答 | 冲突/遗漏清单 + 双向溯源 |
| 检查方式 | 人读 Wiki 自己发现问题 | 系统自动逐项比对 |
| 数值处理 | 自然语言摘要（模糊） | 结构化存储（精确比较） |
| 跨文件对应 | 隐式（靠主题归类） | 显式（CORRESPONDS_TO 边） |

**结论**：DeepWiki 适合"快速了解一个项目的全貌"，但不能替代精确的跨文件一致性审查。可以作为审查员的辅助阅读工具，但不是主链路。

### 5.5 LlamaIndex PropertyGraphIndex ✓

**是什么**：LlamaIndex 的属性图索引模块，支持 Schema 约束的知识抽取 + Neo4j 存储。

**为什么选它**：
1. `SchemaLLMPathExtractor` 支持传入自定义 schema，强制 LLM 只抽取预定义的实体和关系类型——这正是我们需要的
2. 与 Neo4j 有原生集成
3. 有 validation_schema（三元组白名单），可以丢弃不符合本体的抽取结果
4. 社区活跃，文档完整

**角色定位**：用于模块二的关系抽取和模块三的图构建。不用于对齐和检查（那部分自研）。

### 5.6 最终选型结论

没有任何一个框架能端到端解决我们的问题。选择 **LlamaIndex PropertyGraphIndex + Neo4j 作为底座**，在此之上自研对齐引擎和检查引擎。

核心 IP 在自研部分：
- Claim 归一化设计
- SemanticFragment 语义片段设计（覆盖描述性文字的隐含矛盾）
- 4 通道 Blocking 对齐算法 + 3 层 Fragment Blocking 漏斗
- 22 条 Cypher 检查规则（含 3 条语义级矛盾检测规则）
- LLM-as-Judge 逻辑推理比对 prompt 工程

## 六、为什么不用纯 RAG？为什么不用纯规则？

### 6.1 为什么不是纯 RAG

RAG（Retrieval-Augmented Generation）解决的问题是："给一个问题，从文档中找到相关段落，生成答案。"

我们的需求不是问答，而是全量审计。区别在于：

| | RAG 问答 | 全量审计（我们的需求） |
|---|---|---|
| 触发方式 | 人提问 | 系统自动扫描 |
| 检查范围 | 与问题相关的段落 | 所有文件的所有参数 |
| 输出 | 一个答案 | 一份完整的冲突清单 |
| 对齐需求 | 按 query 召回 top-k | 全量 pairwise 对齐 |

如果用 RAG，你需要人工逐条提问"需求书里的测温精度和检测报告一致吗？""电池寿命在各文件中一致吗？"——这等于还是人工审查，只不过查的方式从翻文件变成了打字。

### 6.2 为什么不是纯规则引擎

纯规则引擎（如"需求书第3行的值必须等于设计输入第12行的值"）的问题：

1. **脆弱性**：文件格式稍有变动（加了一行、改了标题），规则就失效
2. **不可扩展**：每个项目都需要重新人工编写几百条规则
3. **无法处理语义等价**：不同表述方式的同一概念，纯规则匹配不上

我们的方案是**先用 LLM 做语义理解（抽取 + 归一化 + 对齐），再用确定性规则做检查**。LLM 负责"读懂"，规则负责"判对错"——两者各取所长。

## 七、与商用 ALM 工具的对比

市面上有 Jama Connect、Matrix Requirements、Greenlight Guru 等医疗器械 ALM（Application Lifecycle Management）工具，它们也有追溯矩阵功能。区别在于：

| | 商用 ALM | 我们的系统 |
|---|---|---|
| 适用场景 | 在系统内创建新文件、手动建链 | 审查已有的历史文件 |
| 追溯关系 | 人工手动挂链 | 自动从文件内容推断 |
| 一致性检查 | 基于人工建立的链接 | 基于语义理解的对齐 |
| 历史文件支持 | 需要重新录入 | 直接导入原始文件 |

简言之：ALM 解决"以后怎么规范地写不出错"，我们解决"一堆已有文件怎么自动审出问题"。两者互补。

## 八、Claim 归一化——为什么这是整个方案的关键

### 8.1 问题本质

跨文件对齐的难点在于：**同一技术参数在不同文件中的表述形式可能完全不同。**

- 语言不同：中文 vs 英文
- 术语不同：精度 vs accuracy vs 允差 vs maximum permissible error
- 粒度不同：需求书写"测温精度±0.2℃"，软件规格写"算法输出精度±0.15℃（为整机留余量）"
- 格式不同：正文段落 vs 表格单元格 vs 列表项

直接做段落级别的 embedding 相似度匹配，召回率和精确率都不够。

### 8.2 解决思路

**把问题从"文本匹配"转化为"结构化记录匹配"。**

当我们把每条事实都抽取为 `(subject, attribute, value, unit, condition)` 这样的固定格式，并且通过术语归一化表把 subject 统一成标准词，那么：

- "测温精度±0.2℃" → `{subject: measurement_accuracy, attr: tolerance, value: 0.2, unit: ℃}`
- "accuracy: ±0.3°C" → `{subject: measurement_accuracy, attr: tolerance, value: 0.3, unit: ℃}`

两者的 subject + attribute 完全相同 → **按 key join 即可对齐，不需要文本相似度。**

这就是把一个模糊的 NLP 问题（文本匹配），转化为一个确定的数据库问题（按 key join）。

### 8.3 为什么能 work

前提条件：术语归一化表的质量足够好——同一概念的各种变体表述都能被映射到同一个 subject 标准词。

这个前提在我们的场景中是可满足的，因为：

1. 医疗器械的技术参数是有限且标准化的（一个产品通常只有 50-100 个独立参数）
2. 术语表可以从法规标准中推导（ISO/IEC 标准对术语有明确定义）
3. 可以用 LLM 辅助生成术语表（先无约束抽取 → 聚类 → 人工审核）
4. 术语表在同类产品间高度复用

## 九、对齐引擎的 Blocking 策略——为什么分 4 个通道

### 9.1 为什么需要 Blocking

3000 个 Claim 两两比较 = 450 万对。每对调 LLM 需要 ~1 秒 + ~0.01 美元。全量比较需要 52 天 + $45,000。不可行。

Blocking 的目标：先用低成本方法快速筛出"可能对应"的候选对（约 2000 对），再只对这 2000 对调 LLM 精判。

### 9.2 四通道设计的互补逻辑

| 通道 | 利用的信号 | 优势 | 劣势 |
|------|-----------|------|------|
| A: ID锚点 | 共享编号（REQ-007等） | 精确率极高(>90%) | 只能对有显式编号引用的对生效 |
| B: Subject匹配 | 归一化后的 subject 字段 | 覆盖面广，是主要候选来源 | 精确率中等(~60%)，需后续验证 |
| C: 本体约束剪枝 | DHF阶段间的对应规则 | 大幅减少无效对（剪枝40%） | 不产生新候选，只做过滤 |
| D: Embedding兜底 | 向量相似度 | 能捕获非典型对应 | 精确率最低(~30%)，噪声多 |

四通道的设计逻辑是"精确率递减、覆盖面递增"——A 通道最精确但只覆盖一小部分，D 通道噪声最多但确保不遗漏。多通道合并确保了既有高精确率又有高召回率。

### 9.3 本体约束矩阵（通道 C）

DHF 流程规定了哪些阶段的文件之间存在逻辑依赖。我们将其编码为"阶段对应矩阵"——只有矩阵中标记为 YES 的阶段组合才保留为候选：

| | 01立项 | 03风险 | 04设计输入 | 07软件 | 08 T1验证 | 09设计输出 |
|---|---|---|---|---|---|---|
| 01立项 | - | | YES | | YES | |
| 03风险(02) | | - | | | | |
| 03风险(03) | | YES(02↔03) | | | | |
| 04设计输入 | YES | | - | YES | YES | YES |
| 07软件 | | | YES | - | YES | |
| 08 T1验证 | YES | | YES | YES | - | |

不在矩阵中的跨阶段对（如"01立项 vs 10试产"）直接剪掉，不进入后续 LLM 判断。

## 十、抽象语段处理策略——SemanticFragment 设计详解

### 10.1 问题本质：检查引擎的"盲区"

现有的 Claim 归一化机制能精确处理**可量化**的技术参数（数值、范围、阈值等），但 DHF 文档中大量内容是**描述性文字**，无法被抽取为 Claim。这些内容如果只是保存在 Section.content 字段中，对检查引擎完全不透明——即使其中包含关键的隐含约束或假设。

**典型盲区示例**：

| 类型 | 举例 | 为什么是盲区 |
|------|------|-------------|
| 隐含约束 | 软件方案："补偿算法有效范围 16-35℃" | 设计输入声称工作温度 10-40℃，存在 5℃ 未覆盖区间 |
| 前提假设 | 算法描述："假定环境温度变化率 ＜2℃/min" | 无人验证这个假设是否在测试中被满足 |
| 行为描述 | 说明书："温度超过 42℃ 时显示 ERR" | 需确认是否有对应测试用例覆盖此分支 |
| 适用范围 | 方案说明："本设计仅针对额温模式" | 若需求书声称支持额温+耳温，则存在范围冲突 |
| 未关闭问题 | 评审记录："待确认是否需要增加开机自检" | 后续文件中是否已关闭该问题？ |
| 设计决策 | 研发记录："选择 NTC 而非红外阵列因为成本" | 若后续设计中出现红外阵列相关描述则矛盾 |

### 10.2 设计哲学：不放宽 Claim，而是分层处理

一个容易陷入的误区是"把 Claim 的 schema 放宽，让 value 字段可以填一大段中文"。这种做法的问题是：

1. **结构化比较能力退化**：Claim 之间的数值比较（`±0.2 vs ±0.3`）依赖严格的 value/unit 字段，放宽后无法自动比较
2. **检查规则失效**：Cypher 查询中的 `toFloat()` 等数值操作对中文字符串无意义
3. **语义损失**：把一段话强行塞进 Claim 字段，丢失了原文的完整语境

正确做法是**保持 Claim 严格，新增一种专门处理描述性内容的节点类型**：

```
能量化的内容 → Claim（自动数值比较）          ← 高精度，窄覆盖
不能量化但重要的内容 → SemanticFragment（LLM 逻辑推理比较）  ← 中精度，宽覆盖
完全叙述性、与审查无关的内容 → 留在 Section（人工阅读）     ← 兜底
```

### 10.3 信息三层处理模型

```
┌─────────────────────────────────────────────────────┐
│               文档原文（Section.content）              │
└────────────────────────┬────────────────────────────┘
                         │ LLM 分类
            ┌────────────┼────────────┐
            ▼            ▼            ▼
    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
    │   可结构化    │ │ 不可结构化    │ │ 与审查无关   │
    │  （有数值）   │ │（有隐含约束） │ │ （纯叙述）   │
    └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
           ▼                ▼                ▼
    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
    │    Claim     │ │Semantic      │ │ 留在 Section │
    │  数值比较    │ │Fragment      │ │ 人工阅读     │
    │  自动检查    │ │ LLM 推理比较 │ │ G3规则标记   │
    └──────────────┘ └──────────────┘ └──────────────┘
```

### 10.4 SemanticFragment 与 Claim 的桥梁：`related_subjects`

`related_subjects` 是整个 SemanticFragment 设计的关键字段。它的作用是：

**建立描述性文字与结构化世界之间的联系**。

当 LLM 抽取一段描述性文字时，即使无法把它变成 Claim，也会被要求回答："这段话和哪些技术参数相关？"答案从术语归一化表中选择（分类任务，不是生成任务），准确率高。

这样在对齐阶段，系统就能自动把"相关的"SemanticFragment 和 Claim 配对：

```
SemanticFragment.related_subjects ∩ Claim.subject ≠ ∅  →  进入候选对
```

**示例**：

| SemanticFragment | related_subjects | 会与哪些 Claim 配对 |
|------------------|------------------|---------------------|
| "补偿算法有效范围 16-35℃" | [operating_temperature, measurement_accuracy] | 所有 subject=operating_temperature 或 measurement_accuracy 的 Claim |
| "本方案仅针对额温模式" | [measurement_mode, product_function] | 所有 subject=measurement_mode 的 Claim |
| "假定环境温度变化率＜2℃/min" | [operating_temperature, response_time] | 所有 subject=operating_temperature 的 Claim |

### 10.5 工程保障：防漏 + 控成本

**防漏措施**（宁可多配，不可漏配）：

1. Prompt 中明确指示"如果不确定是否相关，就标上"
2. Embedding 兜底：对所有 Fragment 和 Claim 计算 embedding，cosine > 0.75 的也拉入候选
3. `topic_tags` 的关键词匹配作为第二安全网

**控成本措施**（避免 LLM 调用爆炸）：

1. 三层漏斗 Blocking（related_subjects → topic_tags → 阶段矩阵）将候选对从数万压缩至 300-500 对
2. 先用 GPT-4o-mini 做初筛（confidence < 0.3 直接丢弃），再用 GPT-4o 对初筛通过的做精判
3. Fragment 数量远少于 Claim（预计 200-400 个 vs 3000 个 Claim），天然控制规模

**成本估算**：

| 步骤 | 候选对数 | Token/对 | 模型 | 成本 |
|------|---------|---------|------|------|
| Fragment 抽取 | 254 文件 | ~2000 | GPT-4o-mini | ~$0.5 |
| 初筛（Fragment vs Claim） | ~500 对 | ~1000 | GPT-4o-mini | ~$0.05 |
| 精判（通过初筛的） | ~100 对 | ~1500 | GPT-4o | ~$0.75 |
| **合计** | | | | **~$1.3** |

相比 Claim 对齐的 $3-50，SemanticFragment 的额外成本几乎可以忽略。

### 10.6 一个完整的 SemanticFragment 工作示例

**原文**（来自"软件方案设计E0"第 4.2 节）：

> 温度补偿算法采用线性插值方式，根据 NTC 传感器采集的环境温度值进行补偿修正。当环境温度低于 16℃ 或高于 35℃ 时，补偿精度不做保证，系统将在界面显示提示信息。

**Step 1: LLM 抽取出 SemanticFragment**

```json
{
  "fragment_id": "SF-042",
  "fragment_type": "constraint_statement",
  "content": "温度补偿算法采用线性插值方式，根据NTC传感器采集的环境温度值进行补偿修正。当环境温度低于16℃或高于35℃时，补偿精度不做保证，系统将在界面显示提示信息。",
  "topic_tags": ["温度补偿", "算法有效范围", "环境温度"],
  "related_subjects": ["operating_temperature", "measurement_accuracy"],
  "source_doc": "软件方案设计E0",
  "source_section": "§4.2 温度补偿算法"
}
```

**Step 2: Blocking 找到候选对**

图中存在 Claim：
```json
{
  "claim_id": "C023",
  "subject": "operating_temperature",
  "attribute": "range",
  "value": "10-40",
  "unit": "℃",
  "source_doc": "设计输入汇总表E0",
  "source_section": "性能Sheet Row5"
}
```

因为 `"operating_temperature" ∈ SF-042.related_subjects` 且 `C023.subject == "operating_temperature"`，配对成功。

**Step 3: LLM-as-Judge 判断**

系统将 SF-042 和 C023 打包送给 LLM，LLM 返回：

```json
{
  "has_conflict": true,
  "conflict_type": "range_mismatch",
  "explanation": "设计输入声称工作温度10-40℃，但软件算法补偿仅在16-35℃有效，存在10-16℃和35-40℃共9℃的未覆盖区间，在此区间内测量精度无法保证",
  "severity": "HIGH",
  "confidence": 0.92
}
```

**Step 4: 写入图 + 出现在审查报告中**

```
[HIGH] 语义片段矛盾 (G1规则)
  片段: 软件方案设计E0 / §4.2 温度补偿算法
       "...当环境温度低于16℃或高于35℃时，补偿精度不做保证..."
  断言: 设计输入汇总表E0 / 性能Sheet Row5
       operating_temperature = 10-40℃
  矛盾: 算法有效范围(16-35℃)窄于设计输入声称的工作温度(10-40℃)
```

如果没有 SemanticFragment 机制，这个矛盾**永远不会被自动发现**。

## 十二、一个贯穿全流程的完整示例

以"测温精度 ±0.2℃"这一参数为例，演示整个系统如何工作：

### Step 1: 格式转换后

客户需求书的 Excel 表格第 7 行变成：
| REQ-PERF-007 | 性能 | 测量精度 | ±0.2℃(35-42℃) | 黑体炉标定 | |

### Step 2: 信息抽取后

LLM 从中抽取出一个 Claim：

```json
{
  "claim_id": "C001",
  "subject": "measurement_accuracy",
  "attribute": "tolerance",
  "value": "0.2",
  "unit": "℃",
  "condition": "35.0-42.0℃",
  "raw_text": "测量精度：±0.2℃(35-42℃)",
  "source_doc": "客户需求书E0",
  "source_section": "需求清单 Row7"
}
```

同时，从检测报告的 6.2 节抽出另一个 Claim：

```json
{
  "claim_id": "C047",
  "subject": "measurement_accuracy",
  "attribute": "test_pass_criteria",
  "value": "0.3",
  "unit": "℃",
  "condition": null,
  "raw_text": "结论: PASS (满足±0.3℃要求)",
  "source_doc": "检测报告V1.0",
  "source_section": "§6.2 精度测试 结论"
}
```

### Step 3: 图谱构建后

两个 Claim 节点写入 Neo4j，各自通过 STATED_IN → PART_OF 边连接到各自的文件。

### Step 4: 对齐引擎

Blocking 阶段：C001 和 C047 的 subject 都是 `measurement_accuracy` → 进入同一候选组（通道 B）。

Verification 阶段：LLM 判断：

```json
{
  "aligned": true,
  "relation": "lt",
  "explanation": "C047的判据(±0.3℃)比C001的需求(±0.2℃)宽松，不满足需求约束",
  "confidence": 0.95
}
```

写回图：创建 CORRESPONDS_TO 边（relation=lt）+ CONFLICTS_WITH 边。

### Step 5: 检查引擎

规则 C3（Claim 数值一致性）匹配到这对 Claim：

```
发现: 检测报告的验证判据(±0.3℃)宽于需求书要求(±0.2℃)
严重度: HIGH
位置1: 客户需求书E0 → 需求清单 → Row7
位置2: 检测报告V1.0 → §6.2 → 结论
含义: 检测报告使用了比需求更宽松的通过标准，可能掩盖实际不达标
```

这条发现进入最终审查报告。

### 13.2 新规则扩展

1. 写一条新的 Cypher 查询模板
2. 指定严重度和输出消息模板
3. 注册到规则列表中

不需要修改任何其他模块。

### 13.3 增量更新

当某个文件被修改时，不需要全量重跑：

1. 只对修改的文件重新执行 M1（转换）和 M2（抽取）
2. 在 Neo4j 中删除该文件关联的旧节点/边，导入新的
3. 重新执行 M4（只对涉及该文件的 Claim 重新对齐）
4. 重新执行 M5（全量跑也只需 1 分钟，无需优化）

**目标**：验证"Claim 归一化 + 按 key join"这条技术路线是否可行。

**做法**：

1. 手工选 3 份关键文件（需求书、设计输入、检测报告）
2. 手工转 markdown
3. 用 LLM 抽取 Claim，观察 subject 归一化效果
4. 手工验证：能否正确对齐？能否检出已知冲突？

**成功标准**：对"测温精度"这一参数，能正确对齐 3 份文件的 Claim 并检出数值矛盾。

## 十六、总结

本系统的核心创新不在于用了哪个框架，而在于问题建模方式的转换：

1. **将跨文件对齐从"文本匹配"转化为"结构化 join"** ——通过 Claim 归一化消除表述差异
2. **将一致性检查从"人工逐条比对"转化为"图模式匹配"** ——利用图拓扑天然编码约束关系
3. **将规则库从"人工经验"转化为"schema 推导"** ——schema 设计本身蕴含检查逻辑
4. **将描述性文字从"检查盲区"转化为"可比对的语义片段"** ——通过 SemanticFragment + LLM-as-Judge 覆盖隐含约束和逻辑矛盾

核心 IP：
- Claim 归一化设计（结构化对齐主干）
- SemanticFragment 语义片段设计（描述性内容的矛盾检测）
- 4 通道 Blocking 对齐算法 + 3 层 Fragment Blocking 漏斗
- 22 条 Cypher 检查规则（含 3 条语义级矛盾检测）
- LLM-as-Judge 逻辑推理比对 prompt 工程

最终效果：254 份文件，30 分钟全自动审查，输出带精确双向定位的冲突清单。不仅能检测数值级矛盾，还能发现隐藏在描述性文字中的隐含约束冲突。成本低于 $55，可重复执行。
