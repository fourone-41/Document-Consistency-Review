医疗器械文档一致性审查系统

用结构化抽取和知识图谱，把 470 份清洗后文件转成可追溯、可对齐、可自动检查的审查系统。

技术路线概述

模块一：格式转换。完整流程是把 doc、xls、pdf 等原始文件转换成结构化 Markdown，并保留页码、章节、表格行列和来源路径。 模块二：信息抽取。LLM 按 schema 把文档里的需求、设计输入、风险、测试和签审信息抽成结构化事实，效果是每条信息都有类型、字段和原文来源。 模块三：图谱构建。把结构化事实导入 Neo4j，并用统一术语、编号和关系边连接不同文件，效果是形成可以查询的跨文件关系网。 模块四：对齐引擎。通过 ID、subject、本体关系和 embedding 找到“不同文件里说的是同一件事”的内容，效果是把人工难发现的跨文档对应关系自动连起来。 模块五：一致性检查。在对齐结果上执行规则和语义判断，效果是输出冲突、遗漏、退化、签审异常等问题，并能定位回具体文件位置。

一句话：先把文档变成结构化事实，再把事实连成知识图谱，最后在图谱上做自动审查。

下周工作计划：测试并实现关系抽取方案

基于《跨文件关系抽取技术调研报告》，把 13 种候选方案转成可验证的实验任务和工程实现卡片。

目标 验证跨文件关系抽取的召回率、准确率、证据可追溯性和运行成本。
输入 当前 schema、edges.yaml、术语表、3 份试点图谱和一批清洗后 Markdown。
产出 候选边、证据 spans、评测表、优先级结论和可并入 Step2/Step4 的实现方案。
验收 每条方案至少完成小样本测试；优先落地 2-3 个对现有管线改动小、收益高的方法。
A1ATLOP：局部上下文池化文档级 RE

解决问题：同一个实体在判断不同关系时需要看的上下文不同，传统做法让所有实体对共用同一个 embedding，容易把无关信息混在一起。

核心方法：对每个实体对单独计算注意力分布，用高权重 token 生成这对实体专属的上下文向量；再用自适应阈值判断多标签关系。

下周测试：在单文件内选 Risk、Control、Test、Claim 节点对，比较“附近段落上下文”和“LLM 选择关键上下文”两种输入，观察关系分类准确率差异。

实现落点：Step2 中不要只截取实体附近文本，而是先让模型返回判断该实体对所需的关键句，再用“实体字段 + 关键句”做关系判断。

A2DREEAM：关系判断与证据定位合一文档级 RE

解决问题：抽到关系后还要知道它依据原文哪几句话，否则审查报告无法精确回溯，错误边也难以复核。

核心方法：把模型判断关系时的注意力当作证据信号，输出关系类型的同时输出支持句子，不额外训练证据分类器。

下周测试：给 Step2/Step4 的 prompt 强制增加 evidence_spans 字段，检查证据句和关系判断是否逻辑一致。

实现落点：每条候选边保存 doc_id、section、text、char_offset。如果证据与关系不匹配，把边降级为 candidate，不直接写入图。

A3AutoRE：关系-头实体-尾实体分解文档级 RE

解决问题：直接让 LLM 在大量关系类型和所有节点对里一步到位选择，候选爆炸且错误率高。

核心方法：把抽取拆成三步：先判断文档里存在哪些关系类型，再找这些关系的 head entity，最后为每个 head 预测 tail entity。

下周测试：把当前 Step2 拆成 Step2a/Step2b：Step2a 输入文档和关系白名单，输出存在的关系类型；Step2b 只在这些关系类型下找实体对。

实现落点：用 Step2a 做低成本过滤器，排除文件中不可能出现的边，例如纯硬件设计方案不生成软件排期类候选。

B1CodRED：桥接实体文本路径跨文档 RE

解决问题：两个文件中的实体往往不是直接相连，而是通过共同出现的产品、编号、人员、部件或术语形成证据链。

核心方法：构建文本路径：源节点上下文 + 桥接实体描述 + 目标节点上下文，再基于这条路径判断跨文档关系。

下周测试：在 merge 结果里查找同时被两个文档引用的 Product、Identifier、Person、标准主题词，作为桥接实体。

实现落点：Step4 不再只把两个孤立节点 description 送给 LLM，而是送“源节点-桥接实体-目标节点”的三段证据链。

B2KXDocRE：外部知识引导跨文档判断跨文档 RE

解决问题：Risk-01、T-12 这类编号节点原文很短，仅凭文本相似度难以判断它们是否存在验证、管控或追溯关系。

核心方法：给节点注入实体类型、法规框架和条款知识，让模型知道 ISO 14971、ISO 13485、IEC 62304 等规则对关系的约束。

下周测试：在 Step4 prompt 中新增“所属法规框架”和“法规知识引导”字段，对比加入法规提示前后的关系判断稳定性。

实现落点：把现有法规知识引导表接进跨文件关系判断，优先约束 Risk-Control-Test、Requirement-DesignInput-Test 这两条链。

B3HCRE：层级式关系分类跨文档 RE

解决问题：让 LLM 一次从 30 多种边里选择，容易在 VERIFIED_BY、COVERS、REPORTED_IN 等近义边之间混淆。

核心方法：把边类型组织成层级树，先粗分类到结构定位、追溯链、验证测试链、风险管控链，再在小类内选择具体关系。

下周测试：把 edges.yaml 按业务粗类重排，写一个两轮 prompt：第一轮判大类，第二轮只在大类内部 3-5 个候选边中选择。

实现落点：低置信度时增加一次验证调用，让模型明确排除相近关系，减少错边进入 Neo4j。

B4MAQD：多角度查询召回候选节点跨文档 RE

解决问题：同一事实在不同文档里表述差异很大，单一 description 向量检索只能命中一部分候选，导致召回不足。

核心方法：为每个节点生成多个角度查询，例如问题描述、影响对象、物理机制、法规视角、解决方向；各角度检索取并集后重排。

下周测试：对 Risk/Claim/Test 节点生成 5 类查询，分别取 top-k 后合并，再用 LLM 或 cross-encoder 重排候选。

实现落点：Step4 候选召回从单一相似度改成“节点描述 + 术语主题词 + 节点类型属性 + 法规术语 + 数值指标”的多路召回。

C1Microsoft GraphRAG：社区摘要层GraphRAG

解决问题：传统 RAG 擅长找局部证据，但不擅长回答“这批文档围绕某主题整体有哪些风险、缺失和冲突”。

核心方法：抽取实体关系后用 Leiden 做社区检测，再为每个社区生成摘要，形成可检索的主题层索引。

下周测试：在当前 Neo4j 图上试跑 Leiden 社区检测，检查是否能把同一风险管控链、同一传感器主题、同一法规主题聚到一起。

实现落点：为社区生成“业务主题摘要”，让审查报告从按文件对罗列升级为按主题组织。

C2LightRAG：轻量双层检索GraphRAG

解决问题：完整 GraphRAG 成本较高，频繁更新或文件规模扩大时社区摘要维护成本会变重。

核心方法：用低层精确 Cypher 查询找具体实体和直接关系，用高层节点描述向量检索找语义相关主题，两层结果合并后交给 LLM。

下周测试：先在 Claim 节点上建描述向量索引，验证“Cypher 精确过滤 + 向量召回”的组合是否能覆盖当前试点问题。

实现落点：作为 GraphRAG 的轻量版本保留，可在文件数增加到几千份或高频增量更新时切换。

D1Graph-RAG 合规检查框架新增技术

解决问题：监管场景下需要判断需求、DHF 文档和法规标准之间是否一致，单纯检索片段不足以支持合规推理。

核心方法：对待检查文档和法规文档共同建图，结合本地检索、全局检索、CoT/ToT 推理，判断文档内容是否违反法规条款。

下周测试：选 2-3 条 ISO 14971/ISO 13485 条款，跑“法规条款-项目文档证据-合规判断”的小闭环。

实现落点：先只用于高价值审查问题，例如风险控制是否验证、设计输入是否覆盖用户需求、软件需求是否有测试证据。

D2远程监督闭环：自动生成训练样本新增技术

解决问题：人工标注关系抽取训练数据成本高，但法规条款中已经隐含大量结构化关系规则。

核心方法：用 ISO 法规中的已知关系三元组自动标注 DHF 文档中共现的实体段落，生成候选正样本，再用降噪策略过滤。

下周测试：从法规知识表抽 3 类关系模板，例如风险控制措施 VERIFIED_BY 验证测试，自动定位文档中的候选段落。

实现落点：先形成小规模人工验证集，评估自动标注质量；质量达标后再考虑 fine-tune 轻量分类模型来替代部分 LLM 调用。

D3Think-on-Graph：图上主动路径搜索新增技术

解决问题：穷举所有候选对成本高，而且难以主动发现追溯链中“应该存在但缺失”的边。

核心方法：把 LLM 当作图上的搜索智能体，每跳先选最有价值的关系类型，再从候选尾实体中剪枝，形成低成本 beam search。

下周测试：从 Risk-01 这类风险节点出发，限制 2-3 跳，测试是否能主动找到 Risk-Control-Test 的缺失路径。

实现落点：全量文件处理后做定期扫描：图里已有 Risk → Control 时，主动追问 Control 是否应有 VERIFIED_BY 的 Test 节点。

D4KG Embedding + 链接预测新增技术

解决问题：图谱变大后，需要快速批量扫描全图缺失边，不能每个节点对都在线调用 LLM。

核心方法：用 TransE、RotatE 或 LLM 增强的 KG Embedding 把节点和边压缩成向量，通过链接预测判断某条边是否可能存在。

下周测试：当前图只有数百条边，先不训练正式 embedding；先规范节点 type 和边 relation 字段，准备高质量训练数据。

实现落点：等全量处理后积累到数千条高质量边，再训练 RotatE 批量预测缺失边；它适合全图扫描，ToG 适合针对特定节点深度推理。

多文件 Neo4j 知识图谱可视化

嵌入十几份文件抽取后的 Neo4j 风格图谱，用来展示更接近真实批量文档的节点、关系和查询效果。

怎么用这个界面

  • 顶部查询栏：在 $ 输入框里写类 Cypher 语句后按回车或点 Run；点击输入框（或按 ?）会弹出常用查询示例，点一条即可填入，例如 MATCH (n:Requirement) RETURN n 看所有需求、MATCH (n) WHERE n.label CONTAINS '温度' RETURN n 按关键词搜索。
  • 看节点：节点按类型用颜色区分（文档 / 需求 / 风险 / 测试 / 风险控制等）；单击节点查看它的属性详情（标题、文档类型、版本、日期等）。
  • 读关系：节点间的连线就是关系，如 TRACES_TO 追溯、VERIFIED_BY 验证；用上面对应的示例查询可只看某一类关系。
  • 调整视图：滚轮缩放，拖动空白处平移画布，拖动单个节点可微调布局；右下角 + / − / ⇄ 三个按钮分别是放大、缩小、一键适配全图。

提示：图谱较大时先用 MATCH (n) RETURN n LIMIT 50 只显示前 50 个节点，再按需查询展开，避免一次铺满看不清。
