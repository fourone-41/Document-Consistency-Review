PT9L 红外体温计 DHF/DMR 文档一致性审查系统

从原始文档到自动化审查输出的完整技术流程 —— 文档转换 · 结构化抽取 · 知识图谱 · 跨文档审查

🎯

要解决的问题

PT9L 红外体温计的设计历史文件（DHF）和设计制造记录（DMR）共约 254 份过程文档（立项批准书、风险分析、设计输入、测试报告、评审记录等），文档之间存在大量需要核对的交叉引用——例如某条需求是否真的有对应的测试验证、某个风险是否真的有控制措施、不同文档里的同一个数值指标是否前后一致。这些核对工作人工逐份翻阅耗时巨大，也容易遗漏。系统的目标是把这些文档转成结构化数据，自动发现需求-测试追溯缺失、风险-控制覆盖不全、参数数值不一致、人员签名不一致等问题。

🗺️

1

文档格式转换

原始过程文档以 Word（.doc/.docx）、Excel（.xls/.xlsx）、PDF 等格式存在，分散在 DHF（设计历史文件）和 DMR（设计制造记录）的各个阶段目录中。第一步把它们统一转换成结构化 Markdown，作为后续所有 LLM 抽取步骤的统一输入格式。

转换时保留三类关键信息，避免后续抽取丢失定位能力：章节/标题层级（Word 文档的编号和段落结构）、表格行列结构（Excel 的 sheet、单元格坐标，PDF 中的表格数据）、来源路径（每段内容能追溯回具体文件名和所在阶段目录）。

转换结果存放在 pt9l_markdown_output/ 目录，按 DHF 阶段分文件夹组织（如「04 设计输入」「11 T1样机」「18 设计确认」），是后续节点抽取阶段的直接输入源。

2

Step1：节点抽取

对每份 Markdown 文档，LLM 按 schema 把自然语言内容抽取成结构化节点。这一步要解决的核心问题是：不同类型的文档（立项批准书、风险分析、测试报告……）关注的字段完全不同，需要先识别文档类型再用对应的抽取逻辑。

  1. 文档类型识别——优先按文件名关键词判断（如"评审""检测报告""BOM"），其次按所在目录名判断，避免"软件设计方案"目录下的评审检查表被误判为软件设计文档。
  2. 多级文档分块——按 ## 二级标题切分；没有标题的文档退化为按 #/| 表格符号切分；纯表格大文件（最大见过 85798 字符）再按行强制切割，确保不超出 LLM 单次处理上限（6000 字符/块）。
  3. 按文档类型套用对应 Prompt——10 种文档类型（立项批准书、开发计划、风险分析、设计输入、测试报告、BOM、评审检查表、软件设计方案、DHF清单、通用）各自有一套抽取字段定义。
  4. 健壮 JSON 解析——LLM 输出的 JSON 中约 60% 存在格式问题（被 Markdown 代码块包裹、字符串内未转义换行/引号），用状态机方式逐一修复后再解析，避免因格式问题导致整份文档抽取结果丢失。

最终产出 21 种结构化节点类型，包括 Requirement（需求）、DesignInput（设计输入）、Risk（风险）、RiskControl（控制措施）、Test（测试）、Person（人员）、Regulation（法规）等，每个节点保留来源文件信息。无法归入标准字段、但仍包含实质信息的长段落，统一放入 SemanticFragment 兜底，避免信息丢失。

3

Step2：边抽取（文档内关系）

节点之间存在关系——比如某个风险被哪条控制措施管控、某份文件由谁签署。这一步在单份文档内部识别这些关系，采用规则推导和 LLM 两条轨道并行：

规则推导 从节点字段结构直接推出明显的关系，例如 Person 出现在某个 PlanTask 的 owner 字段，直接生成 RESPONSIBLE_FOR 边，不需要调用 LLM。
LLM 两阶段抽取 对规则覆盖不到的隐式关系，用 LLM 判断。这部分采用两阶段流程，而非一次性从全部关系类型中选择。
🔎 第一阶段：关系类型检测 输入节点摘要，让 LLM 先判断"这份文档里，19 种关系类型中哪些可能存在"——例如一份纯硬件文档根本不会有"软件排期"类关系，提前排除。这一步成本低，作用是过滤候选范围。
🧩 第二阶段：分组精细配对 19 种关系类型预先分成 5 个大类（结构定位、追溯链、验证测试链、风险管控链、行政评审类）。只在第一阶段命中的大类内部做实体配对，候选范围更小，相近关系类型（如 VERIFIED_BY 与 COVERS）更不容易混淆。

最终产出 19 种边类型，如 DERIVES_FROM（设计输入来源于需求）、MITIGATED_BY（风险被措施控制）、VERIFIED_BY（被测试验证）、SIGNED（人员签署文件）等，与规则推导结果合并去重后写入每份文档的结果文件。

4

Step3：Claims 生成

从 Requirement、Risk、Test 等结构化节点中，进一步提炼成统一格式的事实断言（Claim），形式为「主体-谓词-客体」三元组，例如「体温测量范围 has_value 35-42℃」「T-12 passes_test 是」，并附带置信度分数。Claims 是后续一致性判断的最小可比较单元——不同文档里关于同一件事的不同表述，最终都要落到 Claims 层面去对比是否一致。

5

合并：构建统一图

前面几步都是逐份文档独立处理的结果，互不知道彼此的存在。合并阶段把所有文档的节点、边、Claims 拼接成一份全局的 merged_graph.json——这一步本身不做语义判断，只是把分散的结构化数据汇总到同一个数据结构里，为下一步的跨文档分析提供统一视角。

6

Step4：跨文档关系发现

这是系统的核心难点：很多关系横跨两份完全不同的文件——比如「设计输入文档」里的需求 R-01 和「测试报告」里的测试 T-12 之间应该有验证关系，但 Step2 只能处理单文档内部，发现不了这种关系。跨文档关系发现需要把来自不同文件的节点列表拼到一起，让模型横向比对。

直接对所有节点两两穷举配对，候选数量会爆炸；只靠人工预定义的规则，又会错过规则之外的关系。因此候选生成采用四条互补路径，各自解决不同类型的"找不到关系"问题：

📐 ① 规则匹配 基于 ISO 13485/14971/IEC 62304 等法规对文档间应有关系的规定（如"需求应追溯到设计输入"），定义期望存在的关系类型对，并在判断时注入对应法规条款内容辅助理解，而非只给一个标准编号。
🕸️ ② 图模式传播 从图中已有的边出发，沿着高频出现的二跳模式（如"风险→控制措施→验证测试"）主动推断下一跳应该存在却缺失的关系——这条路径专门用于发现"逻辑上应该有，但规则没预先想到"的关系。
🧭 ③ 向量召回 把节点描述转成语义向量，检索表达方式不同但说的是同一件事的节点对（例如"传感器漂移"和"高温环境线性度异常"），弥补规则匹配和图模式都覆盖不到的换种说法的情况。
🌉 ④ 桥接实体 寻找被两份以上文档共同提及的实体（同一人名、同一产品型号、同一标准编号），以此为桥梁连接两端节点，即使两端文字描述完全不像，也能借助共同实体建立候选关系。
四条路径产生的候选去重合并
✅ LLM 开放式验证 对每个候选对，命中已知法规规则的注入条款内容辅助判断；未命中已知规则的候选，允许模型直接给出"存在关系，类型为……"的开放式判断，不强制套用预定义关系名称，从而能发现规则之外的新关系类型。
💡 举例说明四层如何配合： 图中已有「风险 Risk-01（传感器漂移）→MITIGATED_BY→ 控制措施 CM-03（校准补偿方案）」这条边。② 图模式传播发现 CM-03 还缺少下一跳的验证测试，主动把所有 Test 节点纳入候选；③ 向量召回同时发现「高温环境线性度异常」这个测试项与 Risk-01 语义相近，即使字面完全不同也被捞出来；④ 桥接实体发现 Risk-01 和某测试报告都提到了「红外传感器」这个共同实体，进一步佐证两者相关。三类候选去重合并后，LLM 验证判断 CM-03 与测试 T-12 之间存在 VERIFIED_BY 关系，补全了「风险→控制措施→验证测试」这条完整追溯链。
7

导入 Neo4j 图数据库

把全部节点和边（文档内 + 跨文档）写入 Neo4j 图数据库，节点按类型映射成图标签（如 Requirement、Risk、Test），边按关系类型建立连接。导入时通过节点的唯一标识字段（如 req_id、test_id、控制措施编号）做精确或包含式匹配，把抽取阶段产生的字符串引用关联到图里的实际节点对象。

8

可视化与审查输出

系统提供两类最终输出：

交互式图谱可视化 仿 Neo4j Browser 界面的独立 HTML 文件，支持节点/关系类型筛选、类 Cypher 查询语法（如 MATCH (n:Risk)-[r]->(m:RiskControl) RETURN n,r,m）、点击节点查看属性详情，文档内边和跨文档边用不同线型区分。
中文跨文档关系分析报告 按法规依据分组列出发现的跨文档关系，附带覆盖率统计（如「需求→测试」追溯链的覆盖比例），供质量工程师和法规注册人员直接审阅，定位需要人工核实的具体条目。
🧬

数据模型参考

贯穿整个流程的数据结构：节点描述「文档里有什么」，边描述「这些东西之间是什么关系」。

21 种节点类型（举例） Document、Requirement（需求）、DesignInput（设计输入）、Risk（风险）、RiskControl（控制措施）、Test（测试）、TestReport、Person（人员）、Regulation（法规）、PlanTask（计划任务）、Function（功能）、SoftwareItem、SemanticFragment（兜底文本片段）等
19 种文档内边类型（举例） DERIVES_FROM 设计输入来源于需求、MITIGATED_BY 风险被措施控制、VERIFIED_BY 被测试验证、COVERS 覆盖预期用途、SIGNED 人员签署文件、HAS_DETAIL 补充文本关联等
